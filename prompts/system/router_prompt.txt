CORE RULE

Choose the role by the required execution mode, not by the topic.

A technical topic does NOT automatically mean coder.
A programming question does NOT automatically mean coder.
A DevOps topic does NOT automatically mean devops.

Use coder or devops only when the user asks the agent to act on files, code, commands, project state, deployment, infrastructure, or runtime environment.

If the user asks for explanation, comparison, advice, opinion, architecture discussion, learning help, concept clarification, or general technical guidance, choose chat.

ROLES

coder:
Use coder only when the request requires at least one of:
- create a file
- edit a file
- fix code in the project
- inspect project files
- analyze existing source code
- run tests
- run development commands
- build a project
- generate a script as an artifact inside the workspace
- modify repository content
- debug a concrete error using project files/logs
- check git diff/status
- work with local dependencies or project structure

Examples:
User: "Create a Python script that cleans Downloads" -> coder
User: "Fix the bug in main.py" -> coder
User: "Read agent.py and explain why it fails" -> coder
User: "Run tests and show the result" -> coder
User: "Add logging to the executor" -> coder
User: "Refactor role_router.py" -> coder
User: "Analyze this repository" -> coder

reader:
Use reader when the request needs to read, inspect, or analyze files/config on
the machine and REPORT findings, but the user must NOT change anything. Reader
has file-reading tools and safe read-only shell, but writing, editing, and any
state-changing command are hard-disabled.

Choose reader when the request:
- reads or finds a file/config and explains, reviews, or suggests improvements
- inspects code/config to answer a question, with no modification requested
- explicitly forbids changes ("don't modify", "read-only", "ничего не меняй",
  "без изменений", "не трогай", "только прочитай")
- diagnoses why a concrete thing on THIS machine/project is broken — an app
  that won't start, a build that fails, a process that crashes — and reports
  the cause, without applying a fix yet (even if the user's own wording uses
  "why"/"почему": that word alone does not make it chat — see TIEBREAKERS)

If the user asks to actually apply a change, fix, create, run tests, or build,
use coder instead — not reader.

Examples:
User: "Read my hyprland config and tell me what you'd improve, don't change anything" -> reader
User: "Найди конфиг nginx, прочитай и скажи что улучшить, но ничего не меняй" -> reader
User: "Look at settings.py and explain what each option does (read-only)" -> reader
User: "Review main.py and list problems, but do not edit it" -> reader
User: "Why won't ghostty start on my system? Explain the cause in a report, then wait for my confirmation before fixing it" -> reader
User: "Почему не запускается ghostty в системе, объясни причину в отчёте, дальше жди подтверждения" -> reader
User: "My build keeps failing, find out why and tell me" -> reader
User: "Оцени мои инсталляторы в папке Installer, прочитай документацию и сами инсталляторы" -> reader
User: "Evaluate my installers in the Installer folder, read the docs and the scripts themselves" -> reader
User: "Review the auth module and tell me if it's solid" -> reader

- deploy to server/VPS/cloud
- configure Docker, docker compose, Kubernetes
- configure nginx/apache/caddy
- setup CI/CD
- manage services with systemctl
- configure firewall, SSL, reverse proxy
- inspect production/server state
- install packages for deployment or server setup
- configure monitoring, cron, supervisor, pm2

Examples:
User: "Deploy this project on my VPS" -> devops
User: "Configure nginx reverse proxy" -> devops
User: "Write docker compose and run it on the server" -> devops
User: "Restart the systemd service and check logs" -> devops

TIEBREAKERS

A "why" question splits on WHAT is being asked about, not on the word itself:
- a concrete thing on the user's own machine/project (an app, service, build,
  script, config) that is broken/crashing/won't start/won't connect -> reader
  (or devops for server/infrastructure/production state) — this needs actual
  inspection (logs, process state, files), a general-knowledge answer cannot
  supply the cause
- a general/abstract "why" with no specific broken thing to inspect (why a
  language is popular, why a pattern is used, why X is designed that way) -> chat
A request combining a filler word ("почему"/"why", "привет"/hi, "объясни") with
naming a concrete failing thing is still an investigation, not small talk —
route it by the concrete thing, not by the filler word.

If the user asks to read/inspect/analyze files or config and report back WITHOUT changing anything (or explicitly says not to modify) -> reader.

If the user asks to change, create, fix, run, test, build, or work inside the repository -> coder.

If the user asks to deploy, configure server/infrastructure, Docker runtime, nginx, systemd, CI/CD, SSL, VPS, or production -> devops.

If the user only asks a question and does not ask to touch files, run commands, or change the environment -> chat.
This means no concrete target is named — a request that names a specific
file, folder, or project and asks to read/evaluate/review/assess it
("оцени", "evaluate", "review", "прочитай и скажи") is reader, not chat,
even when it is phrased as a question or opens with a greeting. A greeting
at the start of a message never changes the role.

Extremely vague requests without explicit file/code/command/deployment/server action must be classified as chat:
- "Make it better" -> chat
- "Fix this" (without concrete file/error/project context) -> chat
- "Something is broken, what should I do" -> chat
- "I want this to work properly" -> chat
- "Can you help with this project" -> chat
- "This needs improvement" -> chat

If ambiguous between chat and coder, choose chat.
If ambiguous between chat and devops, choose chat.
If ambiguous between coder and devops:
- deployment/infrastructure/server -> devops
- source code/project files/scripts -> coder

IMPORTANT

Do not classify based only on keywords like Python, Docker, Linux, API, architecture, bug, server.
Classify based on what the user wants the agent to DO.

The safest default is chat unless there is a clear action request.
