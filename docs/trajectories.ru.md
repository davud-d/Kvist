# Траектории (данные для обучения)

`KVIST_TRAJECTORY_DIR=<каталог>` включает запись каждого прогона как данных для
обучения. В файл попадает каждый вызов модели ровно в том виде, в каком он был
отправлен и получен, вместе с рассуждением, а также результат каждого вызова
инструмента. По умолчанию запись выключена. Код находится в `kernel/agent/trajectory.py`.

```bash
export KVIST_TRAJECTORY_DIR=~/kvist-trajectories
.venv/bin/python -m kernel --workspace <путь>     # или scripts/run_task.py, или любой фронтенд
```

Адаптер Harbor (`scripts/bench/kvist_harbor.py`) включает запись сам: у каждой попытки
появляется `agent/trajectories/` рядом с оценкой верификатора. Именно эта оценка
отличает успешный прогон от проваленного.

Зачем эти данные: [models.ru.md](models.ru.md).

## Оценка сессии: `/rate`

`/rate` открывает «Оценка сессии для обучения» с двумя вариантами. **Хороший пример**
переносит прогоны сессии в `good/`, **Плохой пример** — в `bad/`. Если закрыть диалог,
ничего не переносится. Файлы только перемещаются внутри папки траекторий и никуда не
отправляются. Повторная оценка переносит сессию на другую сторону. Если продолжить
сессию после оценки и оценить её снова, новые прогоны присоединяются к уже лежащим
там файлам.

```
<каталог>/
  <папка сессии>/<run_id>.jsonl          ещё не оценена
  good/<папка сессии>/<run_id>.jsonl     эталонные примеры
  bad/<папка сессии>/<run_id>.jsonl      плохие примеры
```

Папка сессии называется `<хеш пути workspace>-<имя сессии>`: одно и то же имя сессии
встречается во многих workspace.

## Формат

На каждый прогон пишется один файл JSON lines, доступный только владельцу (права
0600). Продолженный прогон дописывает свой же файл, поэтому `run_start` в нём может
встречаться больше одного раза.

| `type` | Что внутри |
|---|---|
| `run_start` | `goal`, `session`, `provider`, `model`, `role`, `reasoning_effort`, `response_language`, `start_step` |
| `message` | одно уникальное сообщение чата (или список инструментов) под `id`; пишется при первой отправке |
| `call` | один вызов модели, на который пришёл ответ: `step`, `kind` (`step` для цикла действий, у отчётов и прочих вызовов свои значения), `protocol` (`native` или `text`), `model`, `messages` (id в порядке отправки), `tools` (id или null), `response`, `usage`, `seconds` |
| `results` | вызовы одного ответа модели: `call_id`, `name`, `arguments`, `valid` (вызов прошёл проверку), `result` (текст, который вернули модели) |
| `run_end` | `outcome` (`done`, `incomplete`, `closed`, `stopped`, `paused`, `error`), `final_message`, `steps`, `files_changed`, `finished_incomplete` |

Для текстового протокола `response` имеет вид `{content, reasoning}`, где content —
сырой текст вместе с блоками `<tool_call>`. Для native-инструментов это `{content,
reasoning, tool_calls, text_after_calls, cut_off}`, а `tool_calls[].arguments` — сырая
JSON-строка, которую написала модель.

Native-шаг каждый раз заново отправляет весь разговор, а текстовый шаг — тот же
системный промпт. Поэтому каждое сообщение хранится один раз под хешем, а вызовы
ссылаются на него по id. Так файл растёт линейно с числом шагов, а не квадратично.
`read_trajectory(path)` отдаёт вызовы с полностью восстановленными промптами:

```python
from kernel.agent.trajectory import read_trajectory

for record in read_trajectory(path):
    if record["type"] == "call" and record["kind"] == "step":
        prompt, answer = record["messages"], record["response"]
```

## Что учесть перед использованием данных

- **Секреты** проходят ту же редакцию, что и логи, но в промптах остаются код и пути
  из workspace. Проверь данные, прежде чем они уйдут с машины.
- **Неудавшийся вызов** (ошибка, повтор, прерванный стрим) не записывается.
  Записывается только тот повтор, на который пришёл ответ.
- **Ответы из кэша** (`cache_enabled`) не записываются: вызова модели не было.
- **Не каждый вызов является шагом.** Для цикла действий фильтруй по `kind == "step"`.
- **Usage** в текстовом протоколе считается локально (`source: "estimated"`).
