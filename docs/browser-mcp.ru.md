# Kvist в твоём собственном браузере (`kvist --browser-mcp`)

[English version](browser-mcp.md)

Локальный MCP-сервер, через который Kvist работает в браузере, которым ты и так пользуешься: с твоими
вкладками и входами в аккаунты.

* **Семейство Firefox** (Firefox, Waterfox, LibreWolf): **мост Kvist** — небольшой скрипт, который браузер
  загружает при запуске. Удалённой отладки нет, поэтому сайты видят обычный браузер.
* **Семейство Chromium** (Chrome, Chromium, Brave, Edge, Vivaldi, Яндекс): порт отладки браузера и
  Chrome DevTools Protocol (с ним Chromium по-прежнему сообщает `navigator.webdriver = false`).

Пока Kvist работает во вкладке, на странице видны светящаяся голубая рамка, «пилюля» «Kvist работает
здесь» с текущим шагом и кнопкой **Стоп** и голубой курсор с подписью *Kvist*. Курсор — не картинка
поверх страницы: Kvist ведёт по тому же пути указатель самого браузера, поэтому сайт получает обычные
доверенные события мыши и клавиатуры (наведение, нажатие, отпускание, колесо, ввод по букве).
Нажатие **Стоп** забирает браузер до конца этого хода: Kvist сказано не обходить остановку,
а спросить, что пошло не так и можно ли продолжать; твоё следующее сообщение снова открывает ей браузер.

## 1. Подключи браузер

### Firefox, Waterfox, LibreWolf: мост Kvist

```bash
kvist --browser-bridge install     # копирует мост в ~/.kvist/browser-bridge и печатает следующий шаг
```

Один раз, от администратора, скопируй названный ей загрузчик в папку установки браузера (для Waterfox
это `/opt/waterfox`) и полностью перезапусти браузер:

```bash
sudo cp ~/.kvist/browser-bridge/kvist-autoconfig.cfg /opt/waterfox/
sudo cp ~/.kvist/browser-bridge/autoconfig.js /opt/waterfox/defaults/pref/
```

`kvist --browser-bridge status` показывает, что уже на месте. Новым версиям моста нужны только
`install` и перезапуск браузера. Чтобы убрать мост, удали эти два файла из папки браузера.

Как это работает: загрузчик — штатный autoconfig Firefox, он выполняется с правами браузера. Мост
слушает Unix-сокет, который может открыть только твой пользователь (`$XDG_RUNTIME_DIR/kvist-browser-bridge.sock`),
берёт вкладки прямо из панели вкладок (и выгруженные тоже, не загружая их) и запускает вспомогательный
код Kvist в песочнице каждой страницы. Мышь и колесо отправляются в процессе страницы, клавиши — в окне
браузера, как это делают настоящие устройства; страницы получают доверенные события. Собственные
страницы браузера (настройки, дополнения, `about:`) мост не трогает.

Почему не удалённая отладка: пока Firefox запущен с `--remote-debugging-port`, он сообщает каждой
странице `navigator.webdriver = true`, работает Kvist или нет, и Cloudflare, YouTube и другие считают
тебя роботом (капчи, урезанные функции). К тому же порт ломается на вкладках, восстановленных, но ни
разу не открытых (Firefox 140). Если порт всё же нужен, `kvist --browser-relay` держит его единственную
сессию, а загрузчик чинит сбой с восстановленными вкладками; подробности — в исходнике `relay.py`.

### Chrome, Brave, Edge, Chromium

Открой `chrome://inspect/#remote-debugging` и включи (свежие версии; обычный профиль) **или** запусти
с `--remote-debugging-port=9222` (Chrome 136+ принимает флаг только с отдельным `--user-data-dir`).
Сервер находит браузер по файлу `DevToolsActivePort`, потом пробует порт 9222; настольные приложения
на Chromium, занимающие 9222 (Spotify, приложения на Electron), он узнаёт и пропускает. Другой порт
задаётся `--browser-endpoint 9333`.

Удалённая отладка отдаёт полный контроль над браузером любой локальной программе, которая подключится
к порту. Выключай её, когда она не нужна.

## 2. Зарегистрируй сервер

```bash
kvist --mcp-op add --mcp-name browser --mcp-payload "{
  \"command\": [\"$(command -v kvist)\", \"--browser-mcp\"],
  \"sandbox\": \"none\", \"network\": true,
  \"readonly_tools\": [\"browser_tabs\", \"browser_snapshot\", \"browser_page_text\", \"browser_screenshot\"],
  \"description\": \"The person's own browser: tabs, logins, clicks and typing\"}"
```

`sandbox` должен быть `none`: серверу нужен сокет моста или локальный порт браузера и папка его профиля.
Добавь инструменты в `confirm_tools` (например `browser_act`), если хочешь подтверждать каждое действие.

## Инструменты

| Инструмент | Что делает |
|---|---|
| `browser_tabs` | список вкладок `t1`, `t2`, … с отметкой той, где работает Kvist |
| `browser_open_tab`, `browser_close_tab`, `browser_switch_tab` | управление вкладками |
| `browser_navigate` | адрес http(s) или `back` / `forward` / `reload` |
| `browser_snapshot` | страница текстом, у каждого элемента управления свой ref (`[e12] button "Далее"`) |
| `browser_page_text` | весь видимый текст, чтобы читать длинное |
| `browser_screenshot` | картинка страницы (ядро пропускает её через Vision-модель) |
| `browser_act` | пачка до 40 шагов: `click` (кнопка, двойной/тройной, `hold_ms`), `hover`, `drag`, `type` (into, clear), `press` (`Ctrl+Shift+T`, `hold_ms`, `repeat`), `scroll`, `wait`, `wait_for` текста; `look: snapshot|screenshot` возвращает взгляд на страницу после последнего шага |

Модели сказано планировать по одному взгляду: шаги, которые уже понятны, идут одной пачкой, а смотреть
снова — только после шага, который меняет экран (новая страница, диалог, «Далее»). Пачка
останавливается на первом неудачном шаге и сообщает, какие шаги не выполнены.

## Как устроено

`kernel/browser_mcp/`: клиент WebSocket на стандартной библиотеке, драйверы CDP и BiDi, путь курсора
(`motion.py`: дуга, профиль скорости minimum-jerk, небольшой перелёт на длинных расстояниях),
инструменты (`controller.py`, `server.py`) и `page/kvist_page.js`. Скрипт страницы работает в
изолированном мире `kvist`: DOM у него общий со страницей, а JavaScript — нет, так что скрипты сайта
не видят и не могут подделать его; оверлей живёт в закрытом shadow root в верхнем слое. Открываются
только адреса `http`, `https` и `about:blank`.
