# Kvist UI API — как делать фронтенды

*(English version: [UI_API.md](UI_API.md))*

Это **полный контракт** для того, чтобы поставить любой фронтенд поверх ядра агента
Kvist — терминал, web-приложение, Electron/JS GUI, Telegram-бота или плагин IDE.
Документ самодостаточен: человек или AI может сделать фронтенд по одному этому файлу,
**не читая Python-ядро**.

---

## 1. Идея

Ядро агента не зависит от фронтенда и никогда не пишет в терминал напрямую. Оно только:

- **отдаёт** то, что производит — живой статус, рассуждения плана/шага, стриминг
  текста, финальный ответ, ошибки; и
- **спрашивает** то, что ему нужно — выбор из меню, строку текста, секрет или
  подтверждение опасной команды (да/нет) — и **блокируется**, пока не ответят.

Терминал — это лишь фронтенд по умолчанию. Всё остальное — тонкий адаптер поверх того
же контракта. Способов подключения два.

---

## 2. Два режима интеграции

### Режим A — реализовать протоколы внутри процесса (тот же Python-процесс)

Напишите класс с методами `AgentUI` (§5) и, если обрабатываете опасные команды,
`ApprovalGate` (§6), затем внедрите их:

```python
agent    = LocalAgent(client, executor, config, ui=my_ui)   # agent.py
executor = SafeExecutor(workspace, approvals=my_gate)        # executor.py
```

`main.build_agent(..., ui=my_ui)` тоже принимает внедрённый UI и переиспользует
резолв провайдера/моделей/кредов. Режим **синхронный**: агент вызывает ваши методы на
своём потоке, поэтому методы ввода обязаны блокироваться до ответа пользователя.
Подходит для Python-GUI, который уже гоняет агента на worker-потоке.

### Режим B — поток событий (рекомендуется для GUI / web / Telegram / IDE / других языков)

Превратите границу в **данные**: ядро эмитит JSON-сериализуемые события и читает
JSON-ответы. Именно это нужно фронтендам в отдельных процессах и не на Python. Части
(только stdlib, без внешних зависимостей):

- `frontend_protocol.py` — типизированные события (у каждого `to_dict()`) +
  `PROTOCOL_VERSION` + потокобезопасный `FrontendChannel`.
- `event_stream_ui.EventStreamUI(channel)` — это `AgentUI`, который эмитит события;
  методы ввода блокируются на `channel.request(...)`.
- `event_session.EventSession(channel, agent)` — гоняет `agent.run(...)` на
  worker-потоке и отдаёт события; `EventApprovalGate(channel)` превращает
  подтверждения тоже в события.
- `event_stdio.py` — готовый транспорт NDJSON.
- `frontends.py` — универсальный диспетчер `--frontend NAME` (§9).

**Фронтенд не на Python ничего из этого не импортирует.** Он просто запускает ядро как
дочерний процесс и говорит на JSON (§8).

## 3. Запуск фронтенда

```bash
kvist --workspace /path/to/project --frontend stdio      # поток событий по stdio
kvist --workspace /path/to/project                       # терминальный REPL (по умолчанию)
```

- `--frontend terminal` (по умолчанию) → интерактивный терминальный REPL.
- `--frontend stdio` → NDJSON в stdout/stdin (§8).
- `--frontend <name>` → внешний фронтенд `kvist_frontends/<name>.py` (§9).
- `--frontend stdio --resume` → возобновление checkpoint активной сессии вместо
  новой задачи (строка задачи из stdin не читается; §8a).
- `--session-op …` → одна headless-операция жизненного цикла сессий, JSON в
  stdout (§8a).
- `--doctor` → текстовый отчёт о состоянии (модули, интерфейсы, провайдер, ключи, настройки), код 1 при неудачной проверке; `--yes` разрешает тестовый запрос модели
- `--commit-message` → сообщение коммита по набору изменений из stdin, JSON в
  stdout (§8b).
- `--acp` → Agent Client Protocol по stdin/stdout, для хостов вроде Zed (§8d).
  Рабочая папка приходит с `session/new`, поэтому `--workspace` не используется.
  `--login` действителен только с ним: настроить ключи провайдера в этом
  терминале и завершиться. Это не поток событий NDJSON и `PROTOCOL_VERSION` тут
  не участвует: это JSON-RPC-участник, а что он умеет и чего не умеет для
  конкретного хоста, записано в
  [`frontends/zed/README.ru.md`](../frontends/zed/README.ru.md).

(В разработке, без собранного бинаря:
`.venv/bin/python -m kernel --workspace … --frontend stdio`.)

Необязательные переопределения stdio на один запуск:

```bash
kvist --workspace /path/to/project --frontend stdio \
  --provider omniroute \
  --fast-model ds-web/deepseek-v4-flash \
  --smart-model ds-web/deepseek-v4-pro \
  --role devops \
  --approval-mode ask
```

Переопределения моделей атомарны: передайте оба флага моделей или ни одного.
`--role` принимает `auto`, `coder`, `reader`, `devops`, `chat` или `universal`.
`--approval-mode` принимает `ask` или `deny`; небезопасного режима `allow-all`
намеренно нет.

## 4. Версия протокола и правила совместимости (ПРОЧИТАЙ)

- **Первое событие в любом потоке — `hello`** с полем `protocol_version` (сейчас `1`).
  Проверяйте его; при несовпадении откажитесь или адаптируйтесь.
- **`protocol_version` растёт только при ломающем изменении** существующих форм
  событий/ответов.
- **Добавление нового `type` события — НЕ ломающее.** Фронтенд **ОБЯЗАН игнорировать
  неизвестные типы событий** (forward-compat). Свитч по `type`, неизвестное —
  пропускать.
- В существующее событие могут *добавляться* поля без смены версии; не полагайтесь на
  точный набор ключей — читайте только нужные.

## 5. `AgentUI` — поверхность вывода + ввода (`ui.py`)

Структурный `typing.Protocol` (наследование не нужно). Методы по группам:

**Живой статус / рассуждения (fire-and-forget):**
`start_live()`, `stop_live()`,
`update_live(user_message, status, step, progress=0, plan_step="working", is_error=False)`
(`progress` вычисляется рантаймом по фазе вызовов ответа; модель его не сообщает),
`print_plan(markdown)` (план, который предлагает модель, до вопроса «принять?»), `print_step_header(step, command)`, `debug_print(message)`.

**Ответы:**
`print_final(final_message, user_messages=None)`, `print_user_markdown(message)`,
`print_result(message)`, `print_notice(message, level="info")` (вне диалога: тост, а не ответ; им пользуется уведомление об обновлении), `print_error(message)`, `print_sandbox_notice(note)`,
`render_user_markdown(message, fallback_style="") -> str`,
и стриминг через `live_markdown()` — контекст-менеджер, отдающий callback
`update(message)` (каждый вызов заменяет весь отрендеренный ответ новым кумулятивным
текстом). У callback может быть атрибут `update.reasoning(message)` — второй канал,
стримящий кумулятивный текст раздумий модели; вызывающий берёт его через
`getattr(update, "reasoning", None)`, поэтому UI без канала раздумий продолжают работать.

**Ввод (блокирующий, возвращает ответ):**
`choose_option(title, options, current_value="", help_text="") -> str | None`,
`prompt_text(title, current_value="", help_text="") -> str | None`,
`prompt_secret(title, current_value="", help_text="") -> str | None`.

**Атрибут:** `verbose: bool`.

По умолчанию: `terminal_banner.TerminalBannerUI` (Rich; без TTY вырождается в простой
поток лог-строк).

## 6. `ApprovalGate` — подтверждения с участием человека (`approvals.py`)

Структурный `Protocol` с двумя методами:

- `confirm_command(command: list[str], reason: str) -> bool` — **опасная shell-команда**
  (argv + причина).
- `confirm(title: str, body: str, question: str) -> bool` — **перезапись файла** или
  запрос политики.

По умолчанию `TerminalApprovalGate` рисует запрос и читает y/N; он **fail-closed без
TTY** (бросает исключение, а не молча разрешает). Другой gate внедряется через
`SafeExecutor(workspace, approvals=...)`. В потоке событий `EventApprovalGate`
превращает каждый вызов в `input_request` с `kind == "confirm"` и возвращает
`bool(approved)` — поэтому отключённый/закрытый фронтенд **отказывает** (остаётся
fail-closed).

## 7. Каталог событий

Каждое событие — JSON-объект с полем `"type"`. Исходящие (ядро → фронтенд):

| `type` | Поля | Смысл |
|---|---|---|
| `hello` | `protocol_version:int`; опционально `provider:str, models:object, role:str, approval_mode:str, session:str, has_checkpoint:bool, effort:str, commands:string[]` | handshake и эффективная конфигурация прогона; всегда первым. `effort` (уровень reasoning) и `commands` (имена, которые принимает `command`, включая `resume`, `council` и `best-of`) отправляет `--frontend stdio-multi`. |
| `manifest` | `roles:object[], effort_levels:object[], providers:object[], model_roles:string[], default_models:object, action_types:string[], slash_commands:object[], plugin_commands:object[], plugin_problems:string[], api_settings:object[], styles:object[], themes:object` | Каталог метаданных ядра, формируемый `core_manifest.build_manifest`; отправляется сразу после `hello`, чтобы фронтенды динамически наполняли пикеры без хардкода. `styles` перечисляет варианты (`{value, description}`); каждый вариант задаёт и голос чата, его ядро выводит само, в манифесте его нет. `slash_commands` — список, который фронтенд предлагает после `/`: `via: "core"` — команду выполняет это ядро (шлите сообщение `command` и рисуйте её диалоги), запись без `via` есть только в терминале Classic Legacy, и предлагать её не нужно. `plugin_commands` (`{name, description, path}`) — простые плагины из общей папки `plugins` и папки проекта ([PLUGINS.ru.md](PLUGINS.ru.md)): предлагайте каждый после `/` рядом со встроенными командами, а набранную строку шлите обычным `goal`, ядро развернёт её само; `plugin_problems` — файлы плагинов, в которых нет годной команды, по строке на файл, их стоит показать предупреждением. |
| `live_start` / `live_stop` | — | живой статус начался / закончился |
| `status` | `user_message:str, status:str, step:int, progress:int, plan_step:str, is_error:bool` | прогресс по шагу; во время вызова `user_message` — подпись вызова, которую строит ядро («читает src/x.py») |
| `step` | `step:int, plan_step:str, thought:str, user_message:str, action_type:str, action_args:object, reasoning_seconds:number, action_description:str, call_id:str, batch_id:str` | один вызов инструмента из ответа модели. `reasoning_seconds` — сколько модель думала перед ним (0, если не думала). `action_description` — подпись вызова, ядро строит её из аргументов («читает src/x.py», `ищет "role" в src/`; у `run_shell` это purpose от модели). `batch_id` называет ответ модели: вызовы одного ответа делят его, их можно показать группой. `call_id` называет вызов, его `action_result` несёт тот же. `thought` всегда `""` (модель его больше не пишет). `user_message` — текст ответа для человека на первом `step` пачки и `""` на остальных, поэтому фронтенд, который показывает его на каждом шаге, покажет его один раз. |
| `action_result` | `step:int, action_type:str, ok:bool, summary:str, output:str, exit_code:int\|null, path:str\|null, first_line:int\|null, lines_added:int\|null, lines_removed:int\|null, patch:str\|null, call_id:str, batch_id:str` | итог одного выполненного действия (сопоставляйте с шагом по `call_id` или по `step`). Читающие вызовы одного ответа выполняются параллельно, поэтому несколько `step` могут прийти раньше своих результатов; результаты всё равно приходят в порядке вызовов. Пишущий вызов, пропущенный из-за упавшей записи в том же ответе, приходит с `ok:false` и сводкой «Skipped: an earlier write failed». `summary` — одна короткая строка («Wrote 3 lines», «Command exited with code 0», «2 matches»). `output` — вывод команды после редакции секретов (`run_shell`, `git_status`, `git_diff`, `delegate_task`) или текст ошибки неудачного действия; ограничен 4000 символами: сохраняются начало и конец, между ними маркер `[... N characters omitted ...]`. `exit_code` задан только у `run_shell` (`null`, если команда отклонена или упала по таймауту). `path` и `first_line` заданы для `write_file`/`append_file`/`replace_in_file`: `first_line` — 1-based строка получившегося файла, с которой начинается записанный текст (`1` для `write_file`, первая строка дописанного текста для `append_file`, первое заменённое вхождение для `replace_in_file`), чтобы можно было нумеровать строки диффа; у неудачной записи `null`. `lines_added`/`lines_removed` — построчный дифф записи, его считает исполнитель, который видел заменённый текст (`null` у всего, кроме успешной записи); нужен интерфейсу, который показывает счётчики по файлам. `patch` — та же запись в формате unified diff (`--- a/PATH` / `+++ b/PATH` или `/dev/null`, затем блоки `@@ -a,b +c,d @@` с тремя строками контекста и скрытыми секретами), чтобы фронтенд показывал изменения файла. Номера строк относятся к самому файлу, прибавлять `first_line` не нужно. Значение `null` у всего, кроме успешной записи, и у записи без изменений; после 200 000 символов дифф обрезается на границе строки и заканчивается `\ patch truncated`. Модель его не видит. Не отправляется для `final_answer`/`report_to_user`/`refuse` и для действий, отклонённых защитой рантайма до выполнения (read-only или отсутствие согласования плана); отказ по лимиту web_search/URL приходит как `ok:false`. |
| `action_output` | `step:int, output:str, call_id:str` | живой вывод выполняющейся команды `run_shell`: приходит, пока она работает, и до её `action_result`. `output` — **снапшот** последнего вывода (не больше 4000 символов, редакция секретов применена ко всему целиком), а не дельта, поэтому заменяйте показанное. События идут не чаще раза в ~120 мс, и последнее не теряется. Это только предпросмотр: полный ограниченный вывод по-прежнему приходит в `action_result`, который завершает живой вывод этого `step`. Команда, которая ничего не печатает, не шлёт ничего. |
| `call_begin` | `call_id:str, tool:str, path:str, description:str` | нативный вызов инструмента, который модель **дописала, пока пишет следующие**. В ответе могут быть десятки вызовов, а `step` каждого приходит, когда рантайм до него дойдёт, то есть после того, как написан последний; это событие позволяет показывать вызовы по одному. Шлётся для каждого вызова, кроме `final_answer`/`report_to_user`/`refuse`, когда началась запись следующего (у последнего вызова ответа его нет: его `step` идёт сразу). `step` с тем же `call_id` дополняет карточку, поэтому фронтенд, рисующий `call_begin`, должен использовать эту же карточку. Только живое событие; текстовый JSON-протокол его не шлёт. |
| `call_stream` | `call_id:str, tool:str, path:str, field:str, line:int, text:str, done:bool` | текст нативного вызова инструмента **пока модель его ещё пишет**: `write_file`/`append_file` шлют `content`, `replace_in_file` — `old_text` и `new_text`. `text` — **дельта** из целых слов, начиная со строки `line` (с нуля внутри поля; дельта может начаться посреди этой строки), её нужно дописывать; слово, которое ещё пишется, ждёт пробела или перевода строки, поэтому секрет скрывается целиком. `done: true` закрывает поле, и его последний `text` может кончаться без перевода строки. `line` равный 0 начинает поле заново (повторный запрос). Не чаще раза в ~50 мс, до `action_result` вызова. Только живое событие; текстовый JSON-протокол и другие инструменты его не шлют. |
| `job_started` | `job_id:str, command:string[], purpose:str, call_id:str` | вызов `run_shell` с `background: true` запустил фоновое задание; сам вызов ответил сразу с идентификатором задания, а процесс продолжает работать. `command` — argv, `purpose` — подпись самой модели, `call_id` — вызов `step`, который его запустил, поэтому фронтенд может прикрепить задание к карточке этого вызова. Записывается в журнал сессии. |
| `job_output` | `job_id:str, output:str` | живой вывод работающего фонового задания: **снапшот** его хвоста (с редакцией секретов, с ограничением), а не дельта, поэтому заменяйте показанное. Не чаще раза в ~120 мс, последнее не теряется. Только «вживую», в журнал не пишется; ограниченный хвост приходит ещё раз с `job_finished`. |
| `job_finished` | `job_id:str, status:str, exit_code:int\|null, output:str` | фоновое задание закончилось. `status` — `exited` (`exit_code` задан), `timed_out` или `stopped` (`job_stop` либо ядро убило его в конце хода; `exit_code` может быть `null`). `output` — хвост после редакции секретов, ограниченный. Без `--wake` задание, которое ещё работает, когда агент отвечает, убивает ядро, поэтому каждый `job_started` получает `job_finished` до `turn_end`. С `--wake` задание продолжает работать после ответа, его `job_finished` приходит между ходами, а за ним ход `wake`. Записывается в журнал сессии, если пришло во время хода. |
| `job_notice` | `text:str, job_ids:string[]` | что рантайм сообщил **модели** о фоновых заданиях (новый вывод, завершения) перед её следующим запросом, ровно в том виде, как увидела модель (с редакцией, с ограничением). Фронтенд может показать это приглушённой заметкой; человеку это не указание. Записывается в журнал сессии. |
| `task_state` | `state:str, reason:str` | жизненный цикл задачи (§8f): `running`, `pause_requested`, `paused`, `resuming`, `cancelling`, `cancelled`, `completed`, `failed`, `awaiting_input`, `idle`. Для `pause_requested` показывайте «ставлю на паузу…», а «пауза» — только когда придёт `paused`. `awaiting_input` — ход упёрся в человека: приходит, когда открывается первый `input_request` хода (подтверждения, вопросы плана, вопрос про лимит шагов, `ask_user`, разрешение навыка), а `running` — когда закрыт последний открытый (ответ, таймаут через `input_closed` или отмена). Приходит во время хода, до его `final`, где лежат завершающие слова для человека. `session_id` — имя сессии; `warned_msg_id`/`closed_msg_id` — номера сообщений человека, после которого было предупреждение и которым разговор закрыт; `reason` — однострочная причина от модели, для логов, а не для человека; `closed_notice` — текст ядра на место поля ввода, на языке сессии. Записывается в журнал сессии. |
| `session_title` | `session:str, title:str` | название сессии стало известно: сгенерировано в фоне сразу после первого пакета действий (по одному сообщению пользователя) или, если ход закончился раньше, по первому завершённому ходу, или задано вручную командой `rename` (§8c). Дополнительное, внеполосное событие — может прийти намного позже `turn_end` хода, который его запустил, а `session` может называть не ту сессию, что активна сейчас, если пользователь успел переключиться, пока шла генерация. |
| `command_result` | `name:str, ok:bool, message:str, effects:object` | только `--frontend stdio-multi`: итог входящего сообщения `command` (§8c). Это последнее событие команды; **`turn_end` после него не приходит**. |

**Фоновые команды оболочки.** `run_shell` принимает необязательный `background: true`. Тогда вызов сразу возвращает идентификатор задания вместо вывода команды, процесс продолжает работать, а его жизнь видна в событиях `job_started` / `job_output` / `job_finished`. В `step` и `action_result` появляются два новых значения `action_type`: `job_output` (аргументы `{job_id, wait?}`: прочитать новый вывод задания или ждать его завершения до `wait` секунд) и `job_stop` (аргументы `{job_id}`: остановить задание). Чтение задания моделью — отдельные вызовы, они не меняют события задания. Ход, закончившийся не финальным ответом (остановить всё, ошибка, лимит), убивает каждое ещё работающее задание; финальный ответ делает то же, если фронтенд не передал `--wake`.

**События best-of и совета.** События самих исполнителей и участников совета (их шаги, ответы, мысли) в основной поток не попадают: они идут в дочернюю сессию каждого, а основной поток несёт только перечисленные выше события, из которых `bestof_status` и `executor_activity` — сводки только вживую. Каждое событие в журнале дочерней сессии несёт `executor_id` (собственный `executor_id` события, если он есть, сохраняется), поэтому фронтенд, читающий такой журнал через `--session-op history`, видит, чьи это события. У обычных событий основной сессии `executor_id` нет. Решения человека ядро просит через `input_request` с `kind: "choice"`, который несёт `body` (что решается), `purpose` и `run_id`.

**Пробуждения (`--wake`).** Фронтенд, который умеет показать ход, начатый не им, передаёт `--wake` вместе с `--frontend stdio-multi` (так делают Ink-приложение и панель VS Code). Тогда финальный ответ оставляет работающих помощниц и фоновые задания в живых, и когда что-то из них заканчивается само (не через `job_stop`, не человеком и не «остановить всё»), ядро проводит ход об этом: `wake`, события хода (сначала `job_notice`/`helper`, потом ответ модели), `turn_end`. Модель сохраняет роль и язык хода, оставившего работу, и этот ход не считается сообщением человека. Пробуждение не начинается, пока идёт другой ход или команда: ядро проверяет снова, когда тот закончится, поэтому цель, отправленная одновременно с `wake`, выполняется сразу после хода-пробуждения. Между ходами ядро пишет события по мере появления (`job_finished`, запрос одобрения от пишущей помощницы), а не держит их до следующего хода. `/new` и переключение сессии останавливают то, что оставила прежняя сессия. В журнале у события `user` хода-пробуждения пустой `text` и `"woken": true`.

### Думающие модели (reasoning)

Некоторые модели «думают» перед ответом, иногда минутами. Kvist выносит эти раздумья
на **отдельный канал**, чтобы они не смешивались с ответом:

- **Детекция динамическая, без статического флага.** Фронтенд понимает, что модель
  думает, в момент прихода `reasoning_start` — не по имени модели. Если ответ пошёл
  без событий `reasoning_*`, значит модель не думала; рендерите как обычно.
- **`stream_id` раздумий совпадает с `stream_id` ответа.** Привязывайте UI раздумий к
  тому ответу, который они предваряют.
- **Порядок** для думающего ответа: `stream_start` → `reasoning_start` →
  `reasoning_chunk`* → `reasoning_commit` → `stream_chunk`* → `stream_commit`.
  `reasoning_commit` всегда до первого `stream_chunk`, поэтому мысли и ответ не
  перемешиваются. Типичный GUI показывает живой серый блок, пока модель думает, и
  сворачивает его в ярлык «Thought for Ns» (из `duration_seconds`), когда пошёл ответ.
- **Захват пассивный и провайдер-независимый**, только при включённом стриминге. Kvist
  читает reasoning-токены, которые провайдер и так шлёт (`reasoning` /
  `reasoning_content`), и ничего дополнительно не запрашивает. Учтите: собственные
  reasoning-модели OpenAI (o-серия) **не** стримят текст раздумий через
  `chat.completions` — придёт `reasoning_commit` (время), но серый блок останется
  пустым, и это честно.
- В структурном цикле coder/devops раздумья каждого шага стримятся так же, но отдельным
  потоком: `reasoning_start` → `reasoning_chunk`* → `reasoning_commit` с одним
  `stream_id`, у которого **нет** `stream_start` и нет ответа. Commit приходит, когда
  модель начинает писать действие, а следующее за ним событие `step` несёт
  `reasoning_seconds: 0`, потому что время уже передано. Шаг, на котором модель не
  думала, отдаёт `reasoning_seconds` в событии `step`, как раньше.

Входящий запрос / ответ:

| Поле `input_request` | Заметки |
|---|---|
| `request_id:str` | сопоставьте с ним свой ответ |
| `kind:str` | одно из `choice`, `text`, `secret`, `confirm` |
| `title:str` | короткий запрос |
| `body:str` | длинный текст (например, diff или argv+причина для `confirm`) |
| `options:object[]\|null` | для `choice`: `[{"value","label"[,"description"]}, …]` |
| `current_value:str` | текущее/дефолтное значение (пусто для `secret`) |
| `help_text:str` | опциональная подсказка |
| `timeout_seconds:number` | опционально (автоматический режим): без ответа за это время считается «нет» |
| `purpose:str` | опционально, приходит только непустым: что решает ответ. `"bestof_decision"` — выбор человеком результата прогона best-of (`run_id` называет прогон); ответы: `accept`, `diff`, `other`, `discard`, `diff:<executor_id>` и `pick:<executor_id>` (§8c, `best-of`), закрытый диалог откладывает прогон. Фронтенд может дать такому диалогу свой вид; тот, кто значение не знает, показывает обычный `choice`, которым диалог и является |
| `run_id:str` | опционально, приходит только непустым: прогон best-of, которому принадлежит диалог (`bestof_started.run_id`) |

Когда ядро перестаёт ждать, оно шлёт `{"type": "input_closed", "request_id", "reason": "timeout"}`:
уберите этот диалог. Ответ, пришедший позже, игнорируется. `reason` равен `"timeout"`, если ответ не пришёл вовремя, и
`"cancelled"`, если человек остановил (`cancel`) или поставил на паузу ход, пока был открыт диалог решения best-of
(`purpose: "bestof_decision"`): прогон ждёт как `pending`, и вопрос должен уйти с экрана. Остальные диалоги стоп не
закрывает. Фронтенд обрабатывает любой `reason` одинаково: убрать диалог.

**Ваш ответ — один JSON-объект:**

- `choice` / `text` / `secret` → `{"request_id": "...", "value": "<ответ>"}`
  (или `"value": null` для отмены).
- `confirm` → `{"request_id": "...", "approved": true|false}`.

**Редакция и секреты:** исходящие текстовые поля редактируются от секретов до попадания
в поток. Значение `secret` **никогда не эмитится наружу** — оно приходит только
входящим как ваш `value`. Не логируйте secret-ответы.

**Режим плана.** Перед изменениями модель может предложить план, и делает это через
описанные выше диалоги, а не отдельным запросом:

1. `input_request` `choice` — предложение. `title` — причина от модели плюс строка о том,
   что сначала план — безопаснее, а сразу делать — быстрее, но рискованнее; два
   варианта `options` со значениями `plan` и `go`. Отмена считается как `go`.
2. Событие `plan` `{"markdown": str}` — предложенный план (короткий Markdown).
   Покажите его карточкой *до* следующего запроса; он же записывается в журнал сессии.
3. `input_request` `choice` с заголовком «Принять этот план?» — значения `accept` и
   `revise`. На `revise` ядро присылает запрос `text` («Что изменить в плане?»);
   ответ уходит модели, она предлагает новый план (ещё одно событие `plan` и ещё один
   `choice`). Отмена любого диалога или пустой текст завершают ход на самом плане:
   сообщение `final` — план с пометкой «не принят», изменений нет.

Ядро спрашивает только через интерактивные фронтенды: фронтенд без `ask_choice`
(headless, `run_task.py`) предложения не получает, а модели не сообщается, что
режим плана существует. По ACP диалоги `choice` из двух вариантов приходят кнопками
разрешения; ACP-клиент без form elicitation отклоняет вопрос `text`, поэтому там
отклонённый план завершает ход на самом плане. Авторам
фронтендов достаточно отрисовать карточку `plan` и обычные диалоги `choice` и
`text`; длинный `title` должен переноситься, а не обрезаться.

## 8. Транспорт stdio-JSON (`--frontend stdio`)

Кросс-процессная, кросс-язычная граница. Правила:

- **Кадрирование:** один JSON-объект на строку (NDJSON), UTF-8.
- **Направление:** события → **stdout**; ваши ответы → **stdin** (по одному
  JSON-объекту на строку).
- **Задача (goal)** — это **первая строка, которую вы пишете в stdin** (родитель
  управляет прогоном), если не передана в командной строке.
- **stdout — чистый JSON.** Ядро перенаправляет всё остальное (логи, случайные
  print, предупреждения) в **stderr**, поэтому stdout можно парсить построчно
  безопасно.
- **Порядок:** stdout строго упорядочен. Первая строка всегда `hello`; прогон
  завершается событием `final` (или `error`), после чего поток закрывается.
- **Модель блокировки:** агент работает на worker-потоке и блокируется на каждом
  `input_request`, пока не увидит соответствующий `input_response`. Не ответите — он
  ждёт; закроется процесс/поток — незакрытые подтверждения **отказывают**
  (fail-closed).

### Пример-транскрипт (реальный захват; `>>>` = stdout, `<<<` = ваш stdin)

```
<<< do the thing
>>> {"type": "hello", "protocol_version": 1, "provider": "omniroute", "models": {"fast": "ds-web/deepseek-v4-flash", "smart": "ds-web/deepseek-v4-pro"}, "role": "devops", "approval_mode": "ask", "session": "default", "has_checkpoint": false}
>>> {"type": "status", "user_message": "Choosing provider", "status": "working", "step": 1, "progress": 10, "plan_step": "inspect", "is_error": false}
>>> {"type": "input_request", "request_id": "b7dca6b0…", "kind": "choice", "title": "Pick provider", "body": "", "options": [{"value": "openai", "label": "OpenAI"}, {"value": "freeflow", "label": "FreeFlow"}], "current_value": "", "help_text": ""}
<<< {"request_id": "b7dca6b0…", "value": "freeflow"}
>>> {"type": "final", "message": "picked freeflow …", "user_messages": []}
```

## 8a. Именованные сессии для фронтендов

Каждый прогон выполняется в **активной именованной сессии** workspace (история
диалога, история чата и возобновляемый checkpoint для `/resume` живут в каждой
сессии отдельно). Событие `hello` сообщает это двумя аддитивными полями v1:
`session` (имя активной сессии) и `has_checkpoint` (есть ли в ней
возобновляемый checkpoint).

**Никогда не читайте и не пишите файлы `.kvist/` напрямую.** Управление
жизненным циклом сессий — отдельный one-shot режим того же бинаря без LLM:

```bash
kvist --workspace WS --session-op status
kvist --workspace WS --session-op list
kvist --workspace WS --session-op history --session-name feature [--history-limit N] [--history-before SEQ]
kvist --workspace WS --session-op launch
kvist --workspace WS --session-op input-history                    # последние 100 вводов проекта: {"ok":true,"entries":[старые, …, новые]}
echo "text" | kvist --workspace WS --session-op input-history-add  # UTF-8 в stdin
kvist --workspace WS --session-op new
kvist --workspace WS --session-op create --session-name feature
kvist --workspace WS --session-op switch --session-name feature
kvist --workspace WS --session-op delete --session-name old-work
kvist --workspace WS --session-op reset
```

Каждый вызов печатает **один JSON-объект** в stdout и завершается с кодом `0`
при успехе или `1` при ошибке:

```json
{"ok": true, "active_session": "feature", "sessions": ["default", "feature"],
 "checkpoint": {"goal": "…", "step": 6, "progress": 40},
 "resumable_session": "feature", "warnings": []}
```

`checkpoint` описывает только **активную** сессию; `resumable_session` называет
сессию с самым свежим checkpoint (`null`, если такой нет) — после `launch` это,
как правило, не активная сессия.

**Нативная программа сессий.** `kvist-session` (`kernel/session-rs`, Rust; Linux,
macOS, BSD и Windows) отвечает на те же запросы с теми же аргументами, тем же JSON и
теми же файлами и блокировками, не запуская Python: около 2 мс на операцию
вместо примерно 120. Она необязательна. Ядро ищет её в `KVIST_SESSION_BIN`,
затем как `kvist-session` в `PATH`, затем в сборке рабочей копии
(`cargo build --release` в `kernel/session-rs`; установщик собирает её, когда
есть Rust) и передаёт ей каждый `--session-op`; если программы нет, запрос
обслуживает реализация на Python, так что фронтенду, который вызывает
`kvist --session-op …`, менять ничего не нужно. Если в `KVIST_SESSION_BIN`
указать несуществующий файл, программа отключается.

Как её получает каждый фронтенд: приложение Electron, расширение VS Code и плагин
JetBrains собирают её рядом с упакованным ядром (`npm run build:session`,
`build-plugin.*`), когда есть Rust, и обращаются к ней напрямую за операциями с сессиями;
расширение VS Code делает это только для локального ядра, никогда с `--remote`/`--machine`.
Приложение Tauri и трей находят её рядом с установленным `kvist-core` (её кладёт туда
установщик CLI, устаревшую копию он удаляет) или, из рабочей копии, в сборке крейта; трею
о ней сообщает запустившее его ядро. Rust-интерфейсы, Ink и OpenCode берут
`KVIST_SESSION_CMD` у лаунчера.

Фронтенду, который запускает лаунчер, дополнительно передаётся
`KVIST_SESSION_CMD`: JSON-массив, как `KVIST_CORE_CMD`, — команда, к которой
вместо команды ядра дописывается `--workspace WS --session-op …`. Переменная
задаётся только для ядра на этой машине и убирается в остальных случаях: с
`--remote` сессии принадлежат серверу, и эти операции должны идти через команду
ядра, то есть через ssh-прокси. Фронтенд, который сам запускает ядро,
по-прежнему вызывает ядро.

**Названия сессий.** `title` в каждом элементе `status`/`list` выше вычисляется
заново при каждом вызове (первая цель / первое сообщение чата / цель
checkpoint, иначе имя сессии). Отдельно от этого ядро также генерирует и
*сохраняет* короткое название прямо в документе сессии: один раз, в фоне, сразу
после первого пакета действий (модель видит одно сообщение пользователя) или,
если ход закончился раньше, по первому завершённому ходу (цель плюс первые 20
строк ответа). Если модель не
ответила вовремя, используется первое сообщение пользователя, обрезанное до 40
символов по границе слова, — сессия никогда не остаётся без названия. `rename`
(§8c) задаёт название вручную и с этого момента блокирует фоновую генерацию
для этой сессии. Сохранённое название (или тот же fallback, вычисленный на
лету для сессии, которая появилась раньше этой возможности или ещё не
получила название) — это то, что показывает список интерактивной команды
`session`, и то, о чём сообщает событие `session_title` (§7) в момент, когда
название становится известно — это может произойти заметно позже завершения
хода, который его запустил.

```json
{"ok": false, "error": "Unknown session: 'ghost'"}
```

Семантика (идентична терминальным командам `/session` и `/new`):

- `status` — активная сессия, список сессий, сводка checkpoint (`null`, если нет).
  Каждая запись `session_items` несёт `name`, `title`, `updated_at`,
  `has_checkpoint`, `journal_bytes` (размер журнала событий сессии, `0`, если
  его нет), `closed: true` и `closed_notice` у закрытой сессии (у остальных их
  нет) и предназначенные для модели `session_history` / `chat_history`.
  Эти два поля — вся история каждой сессии, поэтому `status` растёт вместе с
  workspace (~570 КБ на 36 сессий).
- `list` — дешёвый `status`: тот же ответ без `session_history` и
  `chat_history` в записях. Используйте его для выбора сессии; остальной
  `status` не изменился и по-прежнему нужен Electron GUI.
- `history` — журнал событий одной сессии (ниже); ответ для закрытой сессии
  также несёт `closed: true` и `closed_notice`.
- `launch` — **вызывайте один раз при старте вашего приложения.** Запуск всегда
  открывает собственную новую сессию вместо предыдущей. Прерванный запуск не
  теряется: `status` называет сессию, где он остался, в `resumable_session`, а
  `--frontend stdio --resume` сам переключается в неё.
- `new` — создать **и активировать** новую сессию с именем, которое подбирает
  Kvist (терминальная `/new`). Уходящая сессия сохраняется и доступна для
  переключения.
- `create` — то же самое, но с вашим именем; ошибка, если такая уже есть.
- `switch` — активировать **существующую** сессию; отсутствующая или
  повреждённая цель даёт ошибку без смены активной сессии. Переключение никогда
  не создаёт сессии и не трогает файлы workspace.
- `delete` — удалить неактивную сессию (файл + резервная копия). Удаление
  активной сессии отклоняется.
- `reset` — опустошить активную сессию на месте (история, чат, checkpoint);
  имя сохраняется, другие сессии не затрагиваются. В отличие от `new`, это
  **уничтожает** ту переписку, на которой вызвано. Для закрытой сессии
  отклоняется (`{"ok": false}`): опустошение открыло бы её снова.

**Файл нативного разговора.** Рядом с журналом прогон, который говорит с моделью
через её канал инструментов, хранит свой разговор в
`.kvist/sessions/<name>.native.jsonl`: одна JSON-строка на сообщение, строки
дописываются по ходу прогона, так что `/resume` того же прогона на том же
провайдере и модели продолжает его, включая подписанные блоки размышлений
моделей Anthropic. Это собственный файл ядра: фронтенд его не читает, в событиях
и ответах `--session-op` его нет (`protocol_version` остаётся 1, в ответы ничего
не добавляется). Он живёт и умирает вместе с сессией: `delete` и `reset` его
удаляют, а `create` удаляет файл, оставшийся под тем же именем, как и журнал.
Содержимое редактируется так же, как остальное в сессии; размер ограничен
8 МиБ — старые обмены вырезаются целиком, после первых двух сообщений.

**Дочерние сессии (`service`).** Сессия, которую другой агент открыл для своей
работы, несёт в элементе `status`/`list` объект `service`. В нём всегда есть
`kind` и `parent_session` (сессия, которая её запустила), а дальше по виду:

- `helper` — `agent_id`, `parent_run`;
- `executor` (один исполнитель best-of) — `run_id`, `executor_id`, `style`, `branch`;
- `council_member` (участник совета) — `council_id`, `executor_id`, `angle`.

Такая сессия никогда не бывает `active_session` и `resumable_session`, `/resume`
её не предлагает: фронтенд показывает её под `parent_session`, а не среди
разговоров человека. Любой элемент с объектом `service` обрабатывайте так же,
каким бы ни был `kind`. Дочерняя сессия лежит в той же папке `.kvist/sessions`,
что и родительская, даже если её агент работает в другой директории (исполнитель
работает в своём git worktree), поэтому один `list` показывает всю семью.
События в журнале дочерней сессии с `executor_id` несут и этот `executor_id`.

**Итоги токенов и стоимости (`usage`, `usage_total`).** Дополнительные поля
элемента `status`/`list` (`protocol_version` остаётся 1):

- `usage` — всё, что сама сессия потратила за всю жизнь, суммой по каждому
  вызову модели (шаги, роутер, отчёт и т. д.). Есть, только если сессия что-то
  записала. Поля: `input_tokens`, `output_tokens`, `calls`, `cost_approx` и, если
  известны, `cache_read_tokens`, `cache_write_tokens`, `cost_usd` (счётчики кэша и
  стоимость **не передаются**, пока ни один вызов их не сообщил или не имел цены;
  отсутствие поля значит «неизвестно», а не `0`).
- `usage_total` — те же итоги для сессии и всех сессий под ней по
  `service.parent_session`, на любую глубину (цикл в ссылках считается один раз).
  Есть, когда есть что суммировать, поэтому у сессии без детей он равен `usage`.

Стоимость устроена как в событии `usage` (§7): `cost_usd` — сумма известных
стоимостей вызовов, а `cost_approx` равен `true`, если какой-то вызов был
приближённым или без цены, то есть стоимость тогда нижняя граница. Счётчик кэша
складывает только вызовы, которые его сообщили. `reset` обнуляет итоги, новая
сессия начинается с нуля.

### Закрытые сессии

В интерактивном фронтенде (классический терминал, `--frontend stdio-multi`,
`--acp`) у модели есть ещё один инструмент, `end_session`, — для человека,
который после предупреждения оскорбляет её или людей, или сам просит закончить разговор
(уведомление, что закрытие необратимо, затем подтверждающее сообщение и проверка; никогда, если человек
может навредить себе или другим). Всё, кроме одного
суждения, решает ядро: предупреждение (событие `message` с фиксированным
текстом), его свежесть и само закрытие. Закрытая сессия:

- **только для чтения навсегда**. Любую цель и любой `resume` в ней ядро
  отклоняет до маршрутизации и до любого вызова модели: ответ — одно событие
  `final` (`closed: true`, `outcome: "incomplete"`) с фиксированным текстом, в
  stdio-multi затем `turn_end`, и в сессию и её журнал ничего не пишется;
- **остаётся доступной для чтения**: `history`, `list`, `status` и переключение
  на неё работают как обычно, а записи `list`/`status`, ответ `history` и событие
  `session` несут `closed: true` и `closed_notice` — текст ядра на место поля
  ввода, на языке сессии, чтобы фронтенд не зашивал свой;
- пропускается в `resumable_session`, не поддаётся `reset` и не трогает файлы и
  git. Новая сессия (`new`, `launch`) начинается без неё;
- **удаляется как любая другая**: `delete` (session-op и команда `session
  delete`) убирает её вместе с журналом, если она не активна. Это история
  человека: замок запрещает продолжать разговор, а не хранить его.

В ходе chat модель пользуется им, отвечая одним тегом и ничем больше. Такой ответ
никогда не показывается: его поток заканчивается пустым `stream_commit`, а ответ
хода приходит как `message` с предупреждением или `final` с закрытием. Пустой
`stream_commit` ничего не рисует.

В цикле действий слова ответа идут потоком раньше его вызовов, поэтому ответ,
который заканчивается вызовом `end_session`, их уже показал. Тогда его поток
откатывается к пустому (`stream_chunk` с `append: false` и пустым `text`) и
заканчивается пустым `stream_commit`: слова надо убрать. ACP (Zed) умеет только
дописывать и забрать их не может.

Предупреждение (`message`) и завершающие слова (`final` с `closed: true`) — это
речь Kvist: рисуйте их как обычные сообщения Kvist, без рамки статуса, без
отметки «не сделано» и без цвета ошибки. Предупреждение — не незавершённый
ответ, закрытие — не провал задачи.

Что фронтенд показывает в закрытой сессии, одинаково на всех поверхностях:
плашку на месте поля ввода, той же высоты, с `closed_notice` приглушённым
текстом — без красного, без иконок тревоги, без анимации. Она появляется на
живом `session_ended` и при открытии сессии с `closed: true`. Enter открывает
новую сессию обычным для фронтенда путём новой сессии; остальные клавиши ничего
не делают, и напечатать в сессию нельзя никак (ни фокусом, ни вставкой).
История остаётся доступной: скролл, выделение, копирование. Переключение на
другую сессию возвращает поле ввода.

### Восстановление ленты сессии: `--session-op history`

Документ сессии хранит только то, что нужно модели (цель, роль, результат в 200
символов). Отдельно ядро ведёт **журнал того, что видел пользователь**: те же
события, что несёт поток из §8, в том виде, в каком они были отправлены, —
фронтенд перерисовывает старую сессию, проигрывая их через уже имеющийся
reducer. Журнал покрывает каждый ход, в том числе выполненный из терминала или
другим фронтендом.

```bash
kvist --workspace WS --session-op history --session-name feature --history-limit 500
```

```json
{"ok": true, "session": "feature", "has_more": true, "total_events": 1240,
 "skipped_lines": 0, "journal_bytes": 913442,
 "events": [
   {"seq": 812, "turn": 9, "ts": 1758560000.1, "event": {"type": "user", "text": "fix the tests"}},
   {"seq": 813, "turn": 9, "ts": 1758560000.9, "event": {"type": "route", "role": "coder", "source": "llm"}},
   {"seq": 820, "turn": 9, "ts": 1758560014.2, "event": {"type": "action_result", "step": 3, "action_type": "run_shell", "ok": true, "summary": "Command exited with code 0", "output": "12 passed\n", "exit_code": 0, "path": null, "first_line": null}}
 ]}
```

- `events` идут по порядку, старые первыми; `event` — в точности объект события
  из §8. `seq` уникален и растёт в пределах сессии, `turn` нумерует запросы
  пользователя (с 1), `ts` — время записи по настенным часам.
- **Записывается** (уже с редакцией секретов): `route`, `tool_mode`, `plan`,
  `sandbox_notice`, `step` (с полными `action_args`: у шага `run_shell` есть
  argv, у `write_file` — содержимое, у замены — `old_text`/`new_text`),
  `action_result` (вывод, код выхода, путь, `first_line`), мысли как
  `reasoning_start` / `reasoning_chunk` / `reasoning_commit` (**один**
  `reasoning_chunk` с итоговым текстом), ответ как `stream_commit`, `message`
  или `final` (целиком), `error`, события фоновых заданий
  `job_started` / `job_finished` / `job_notice`, события best-of и совета,
  помеченные в §7 как записываемые, и по одному `usage` на ход (`kind: "turn"`,
  суммарные токены).
- **Не записывается** (только «вживую»): `status`, `live_start`/`live_stop`,
  `stream_chunk`, `action_output`, `call_begin`, `call_stream`, `job_output`, `debug`, `usage` по шагам, `hello`,
  `input_request`, `command_result`, `bestof_status`, `executor_activity`, `bestof_diff`.
- **Добавляет сам журнал**: `user` — `{"type": "user", "text": …}`, запрос,
  открывший ход (`"resumed": true` для `/resume`; пустой `text` и
  `"woken": true` у хода-пробуждения), которого в потоке нет;
  `turn_end` закрывает каждый ход (с `"stopped_by_user": true`, если ход
  остановил пользователь); `journal_notice` сообщает, что что-то опущено:
  `{"omitted_events": N}` внутри хода, `{"omitted_turns": N}` первым событием
  журнала, когда старые ходы отброшены.
- Пагинация: возвращаются самые новые `--history-limit` событий (по умолчанию
  500, максимум 5000); `has_more` говорит, что есть более старые, а
  `--history-before SEQ` возвращает страницу, заканчивающуюся прямо перед
  `seq` `SEQ`. Страница может начинаться посреди хода.
- Потолки (усечённая строка сохраняет оба конца и содержит
  `[... N characters omitted ...]`): 20 000 символов на поле (записанное
  содержимое, аргументы, мысли), 100 000 на ответ, 200 элементов в списке,
  2 000 событий и 2 МиБ на ход (у ответов, ошибок и `turn_end` есть небольшой
  запас сверх этого), 8 МиБ и 500 ходов на сессию — сверх этого отбрасываются
  **самые старые ходы целиком**.
- `skipped_lines` считает строки журнала, которые не удалось разобрать (сбой
  может оборвать последнюю); они стоят только самих себя. Отсутствующий журнал —
  пустая история, поэтому сессии, созданные до появления журнала, читаются как
  `events: []`. Неизвестная сессия — `{"ok": false}`.
- Журнал только для показа: в промпт модели он не попадает. Он живёт и умирает
  вместе с сессией — `delete` и `reset` его удаляют, `new`/`create`/`switch` не
  трогают. Если журнал не удаётся записать, ход всё равно выполняется, а
  событие `debug` сообщает об этом.

Чтобы **возобновить** checkpoint активной сессии, запустите событийный фронтенд
с `--resume` вместо строки задачи:

```bash
kvist --workspace WS --frontend stdio --resume
```

Поток — обычный поток из §8; если checkpoint нет **ни в одной сессии**, ядро
отправляет событие `error` («No saved checkpoint to resume.») и завершает
прогон. Иначе ядро само активирует сессию, где он лежит, — поэтому поле
`session` в событии `hello` может отличаться от той, с которой вы запустились.

## 8b. Сообщения коммитов для IDE-фронтендов

Один вызов без потока событий: запишите изменения в stdin как JSON в **UTF-8**,
закройте stdin и прочитайте одну JSON-строку из stdout.

```bash
kvist --commit-message < payload.json
```

```json
{
  "files": [{"path": "src/app.py", "patch": "--- a/src/app.py\n+++ b/src/app.py\n..."}],
  "recent_subjects": ["Fix retry backoff", "Add AnyModel stub"]
}
```

- `files` — по записи на каждый изменённый файл; `path` относителен корня VCS,
  `patch` — unified diff файла. Передавайте то, что пользователь выбрал для
  этого коммита.
- `recent_subjects` — необязательно, заголовки последних коммитов (учитываются
  не больше 15). Сообщение подстраивается под их стиль: Conventional Commits,
  если проект их использует, иначе обычное предложение в повелительном
  наклонении.

Ответ (с ASCII-экранированием, чтобы кодовая страница консоли не мешала):

```json
{"ok": true, "message": "Retry provider calls on 429\n\nThe gateway ..."}
{"ok": false, "error": "Nothing to describe: no changed files with a diff."}
```

Код выхода 0 при успехе и 1 при ошибке. На что фронтенд может опираться:

- Сообщение всегда на английском, заголовок не длиннее 72 символов.
- Используются сохранённый провайдер и его **fast**-модель. Отсутствующий ключ —
  ошибка, а не запрос ввода, поэтому вызов не может зависнуть в ожидании.
- В рабочую папку ничего не пишется: ни сессии в `.kvist/`, ни `KVIST.md`.
- Секретные файлы (`.env`, ключи, сертификаты, `.ssh/`, ...) и `.kvist/`
  отбрасываются до того, как модель что-либо увидит; фильтровать их самим не
  нужно.
- Большой diff обрезается под модель; из-за размера вызов не падает.
- Всё остальное, что печатает ядро, идёт в stderr: его можно логировать, но не
  разбирать.

## 8c. Команды в процессе ядра (`--frontend stdio-multi`)

Слэш-команды и мастера настройки терминала выполняются в том же долгоживущем
процессе. Фронтенд их не переписывает: он шлёт одно сообщение, рисует каждый
диалог команды универсальным видом `input_request` и читает итог из
`command_result`.

```json
<<< {"type": "command", "name": "role", "args": []}
>>> {"type": "input_request", "request_id": "b7dc…", "kind": "choice", "title": "Select Agent Role", "body": "", "options": [{"value": "auto", "label": "Auto (automatic role detection)", "description": "…"}, {"value": "coder", "label": "Coder", "description": "…"}], "current_value": "auto", "help_text": "…"}
<<< {"request_id": "b7dc…", "value": "coder"}
>>> {"type": "command_result", "name": "role", "ok": true, "message": "Role set to: coder / Роль: coder", "effects": {"role": "coder"}}
```

**Многострочная цель.** Цель — обычная строка stdin; текст с переводами строк
идёт как `{"type": "goal", "text": str}` (`stdio-multi`), `text` ставится в очередь как цель.

**Входящее сообщение:** `{"type": "command", "name": str, "args": string[]}`.
`name` — имя слэш-команды без слэша (регистр не важен); `args` необязателен и
заранее отвечает на первый вопрос команды, так что
`{"type":"command","name":"role","args":["coder"]}` вообще не открывает диалог.
Диалоги — обычная пара `input_request` / ответ из §7; ответ `secret` идёт только
внутрь и никогда не отражается наружу: ни в событии, ни в `message`, ни в
`effects`, ни в логах. Разрушительные шаги (`revert`, `del-provider`,
`full-reset`) спрашивают через `kind: "confirm"` с `body`; «да» — только
`approved: true`, всё остальное (`false`, нет ответа, EOF) ничего не делает.

**Правила**

- Команда выполняется **только между ходами**. Пока идёт ход (или другая
  команда), ядро сразу отвечает `ok:false` и команду не запускает.
- Каждая принятая команда заканчивается ровно одним `command_result`; в отличие
  от хода **`turn_end` нет** (кроме команд, которые сами являются ходом, см.
  ниже). Неизвестное имя, отсутствующее имя и неверные `args` тоже получают
  `command_result` с `ok:false`.
- `ok:false` — команда не удалась (`message` объясняет почему). Отменённый
  пользователем диалог — это `ok:true` и `effects` `{"cancelled": true}`, ничего
  не изменилось. EOF на stdin отменяет открытый диалог так же.
- `message` — текст для человека, всегда `English / Русский`, с редакцией
  секретов.
- `effects` говорит, что изменилось, чтобы фронтенд обновил своё состояние.
  Ключи есть только для того, чего команда коснулась.

**Команды и их `effects`**

| `name` | `args` | `effects` |
|---|---|---|
| `role` | `[auto\|coder\|reader\|devops\|chat]` | `{"role": str}` — это же роль, с которой отправляются все следующие цели; сохраняется как глобальная настройка |
| `effort` | `[false\|low\|medium\|high\|xhigh\|max]` | `{"effort": str, "advisory": str}` — `advisory` объясняет, как уровень ложится на активного провайдера (может быть пустым) |
| `verbose` | `[true\|false]` (без аргумента — переключить) | `{"verbose": bool}` — только для этого процесса |
| `style` | `[ИМЯ]` | `{"style": {"name": str, "applied_to_session": bool}}` — один выбор задаёт стиль агента и подходящий ему стиль чата; `false` значит, что текущая сессия сохраняет свои стили до следующей сессии |
| `session` | `[switch ИМЯ]`, `[new [ИМЯ]]`, `[delete ИМЯ]`; без аргументов — выбор из списка | `{"session": str, "sessions": string[], "has_checkpoint": bool, "changed": bool}` |
| `new` | `[ИМЯ]` | как у `session` |
| `export` | без аргументов — диалоги; `list`; `<агент> [all]`; `all`; слово `everywhere` добавляет сессии из других папок. `<агент>` — `claude-code`, `codex`, `opencode`, `cursor`, `qwen-code`, `continue` или `aider` | Импортирует сессии другого агента как новые сессии Kvist (имена `cc-…`, `cx-…`, `oc-…`, `cu-…`, `qw-…`, `ct-…`, `ai-…`; активная сессия не переключается). Без аргументов два диалога `choice`: агент (со счётчиками), затем сессия (с пунктами «Все из этой папки» и «Другие папки…»). `{"imported": [{"session","source","title","turns","turns_in_context"}], "already_imported": int, "empty": int, "failed": string[]}`; у `list` нет `effects`, счётчики — в `message`. Уже импортированная сессия пропускается, не перезаписывается. Отменённый диалог — `{"cancelled": true}` |
| `rename` | `ИМЯ` (обязателен; несколько аргументов склеиваются пробелом) | `{"session": str, "title": str}` — задаёт название активной сессии вручную; с этого момента блокирует фоновую генерацию названия для неё (§8a) |

**`resume`** — не мастер, а ход агента: `{"type":"command","name":"resume"}`
продолжает самый свежий прерванный прогон в той сессии, где лежит его чекпоинт.
Если чекпоинта нет ни в одной сессии, сразу приходит
`command_result {"name":"resume","ok":false,…}` и больше ничего. Иначе поток
ровно такой же, как у обычной цели, плюс одно событие в начале:

```
>>> {"type": "session", "session": "chat-2026…", "has_checkpoint": true}
>>> … события хода (route/plan/step/action_result/… final или error) …
>>> {"type": "turn_end"}
```

У возобновлённого хода **нет `command_result`**; его завершает `turn_end`, а
`session` говорит фронтенду, какая беседа теперь активна. Как и обычный ход, он
не принимает `command`, пока идёт. В закрытой сессии (§8a) `resume` — ход без
события `session`: ответ ядра для закрытой сессии в `final`, затем `turn_end`.

**Команды-ходы: `council`.** `{"type":"command","name":"council","args":[…слова]}`
(слова склеиваются пробелом) или строка цели, которая начинается с `/council `
(обычная строка либо текст сообщения `{"type":"goal"}`), задаёт режиму council из §7
вопрос: четыре участника без права записи смотрят на него с четырёх углов
(`simplicity`, `security`, `speed`, `maintenance`), каждый сдаёт карточку, затем называет главный риск в решении каждого
из остальных (один раунд), и выбирается одно решение. Поток — как у хода, а после
него `command_result`, как у команды:

```
>>> {"type": "council_started", "council_id": "c1…", "question": "…", "members": [{"executor_id": "simplicity", "angle": "simplicity", "session": "council-…"}, …]}
>>> {"type": "council_card", …}  ×4   {"type": "council_objection", …}  ×4   {"type": "council_verdict", …}
>>> {"type": "final", "message": "## council …", "outcome": "done", …}
>>> {"type": "turn_end"}
>>> {"type": "command_result", "name": "council", "ok": true, "message": "council: decision chosen: … / council: выбрано решение: …", "effects": {"council_id": "c1…", "chosen": "security", "decision": "…"}}
```

- `final.message` — весь ответ в Markdown на языке вопроса: вопрос, карточки,
  возражения, выбранное решение с причиной и кто остался против. Фронтенд без
  экрана council показывает этот текст и больше ничего.
- Ход журналируется как любой ход: `user` с набранным текстом (`/council …`), события
  council, `final`, `turn_end`. Собственная работа участников лежит в их дочерних
  сессиях (`service.kind: "council_member"`, §8a).
- `cancel` во время хода останавливает всех участников; ход заканчивается без
  `council_verdict`, `final.outcome` равен `incomplete`, `command_result` — `ok:false`
  с `effects.stopped: true`. Пауза останавливает его так же.
- Без вопроса (пустые или пробельные `args`, либо голая строка `/council`) ответ —
  `command_result` с `ok:false`, хода нет: ни событий, ни `turn_end`.
- `ok:false` бывает и когда пригодную карточку сдали меньше двух участников, когда
  за две попытки не получился допустимый выбор или когда модель не ответила;
  `final` тогда говорит об этом и показывает карточки и возражения, которые есть.
- Как для любой команды, `command` во время хода отклоняется сразу; строка цели
  встаёт в очередь, как встаёт цель.

**Команды-ходы: `best-of`.** `{"type":"command","name":"best-of","args":[…слова]}` (слова склеиваются пробелом)
или строка цели, которая начинается с `/best-of ` (обычная строка либо текст сообщения `{"type":"goal"}`),
запускает режим best-of из §7: `/best-of [N] <задача>`. `N` — необязательное первое слово, число от 2 до 6
(по умолчанию 4): столько исполнителей работают над задачей, каждый в своём git worktree и со своим рабочим стилем
(`senior-dev`, `minimalist`, `paranoid`, `fast-and-dirty`, `perfectionist`, `architect`; прогон берёт первые `N`),
основной агент проверяет то, что они оставили (внутри — в роли проверяющего, которую не называет ни одно событие и
ни один текст), а человек решает, что делать с результатом. Поток — как у хода, а после него `command_result`,
как у команды:

```
>>> {"type": "bestof_started", "run_id": "3fa9c1d2", "task": "…", "count": 2, "base": "9be41f07aa", "executors": [{"executor_id": "e1", "style": "senior-dev", "branch": "kvist/bestof/3fa9c1d2/e1", "session": "bo-3fa9c1d2-e1"}, …]}
>>> {"type": "bestof_status", …}  /  {"type": "executor_activity", …}   (только вживую, много)
>>> {"type": "bestof_eliminated", "run_id": "3fa9c1d2", "executor_id": "e2", "reason": "…"}      (когда проверка отсеивает кого-то)
>>> {"type": "bestof_verdict", "run_id": "3fa9c1d2", "rows": […], "winner": "e1", "reason": "…"}
>>> {"type": "input_request", "request_id": "…", "kind": "choice", "purpose": "bestof_decision", "run_id": "3fa9c1d2", "title": "…", "body": "<таблица вердикта>", "options": [{"value": "accept", …}, {"value": "diff", …}, {"value": "other", …}, {"value": "discard", …}]}
<<< {"request_id": "…", "value": "accept"}
>>> {"type": "bestof_finished", "run_id": "3fa9c1d2", "outcome": "accepted", "message": "…", "executor_id": "e1", "commit": "…"}
>>> {"type": "final", "message": "## best-of …", "outcome": "done", …}
>>> {"type": "turn_end"}
>>> {"type": "command_result", "name": "best-of", "ok": true, "message": "best-of: accepted e1, commit 7c1d… / best-of: принят e1, коммит 7c1d…", "effects": {"run_id": "3fa9c1d2", "outcome": "accepted", "executor_id": "e1", "commit": "…"}}
```

- **Проверка.** Шаги проверки (`step`, `action_result`) идут как у любого хода; своего `final` проверка не шлёт,
  как и события `route`: единственный `final` — это `final` хода, после решения. Ядро сверяет вердикт с тем, что
  исполнители действительно оставили, поэтому `style`, `tests` и `diff` каждой строки `bestof_verdict` — факты
  ядра, а слова проверяющего — только `outcome` и `note`. Победитель — исполнитель, который закончил и
  что-то изменил, либо его нет: если ни один исполнитель не решил задачу, проверка так и говорит,
  `bestof_verdict` приходит с `winner: ""` и без строк с `outcome` `winner`. Победитель с `tests.state` `failed`
  называется, только если красные тесты у всех исполнителей, оставшихся в сравнении. Порядок проверки задан: сначала обман (удалённые или пропущенные тесты, ослабленные assert,
  заглушки, правки не по задаче), потом тесты проекта, потом качество по полным diff финалистов.
- **Диалог решения** — `input_request` с `kind: "choice"`, `purpose: "bestof_decision"` и `run_id` прогона. `body`
  первого диалога — вердикт в Markdown (таблица: стиль, итог, тесты, diff и заметка по каждому исполнителю,
  победитель и причина); подписи — на языке запроса. Значения ответа и что делает каждое:

  | `value` | что делает ядро |
  |---|---|
  | `accept` | принимает победителя: изменение победителя становится **одним** коммитом в текущей ветке человека (сообщение коммита — первая строка задачи, затем стиль победителя и причина); остальные незакоммиченные правки человека остаются незакоммиченными; worktree и ветки исполнителей удаляются; `bestof_finished` `accepted` с `executor_id` и `commit` |
  | `diff`, `diff:<executor_id>` | шлёт `bestof_diff` (патч победителя или названного исполнителя) и задаёт **тот же вопрос снова**, `body` которого теперь патч (обрезан на 20 000 символов); просто `diff` — победитель |
  | `other` | второй диалог, снова `bestof_decision`, по остальным финалистам (`pick:<executor_id>` на каждого и `back`); выбранный принимается как при `accept`; `back` (или отсутствие других финалистов) возвращает к первому вопросу |
  | `pick:<executor_id>` | сразу принимает этого финалиста (фронтенд, который сам перечисляет финалистов, может ответить так на первый диалог); id не из финалистов возвращает к вопросу с пояснением |
  | `discard` | удаляет worktree, ветки исполнителей и папку прогона; файлы и ветка человека не затрагиваются; `bestof_finished` `discarded` |
  | `null` (диалог закрыт или спросить некого) | прогон **откладывается**: `bestof_finished` `pending`, а `final` говорит, как решить позже |

  Набор вариантов зависит от вердикта, а **первый из них — безопасный по умолчанию** (фронтенд открывается на нём): при
  победителе, чьи тесты прошли или не запускались, это `accept`; при победителе с `tests.state` `failed` это `diff`, а `accept`
  по-прежнему предлагается с подписью «всё равно принять, тесты падают»; **без победителя** варианты — только `discard`,
  `diff` и `other` (в этом порядке), `accept` не предлагается: `accept`, всё же присланный в ответ, ничего не принимает и
  задаёт тот же вопрос снова с пояснением. Без победителя `diff` без id показывает первый результат, где что-то
  изменено, а `other` / `pick:<id>` выбирают вручную среди всех результатов с изменениями (не только среди финалистов).
  В `body` на месте победителя стоит «нет», а при победителе с красными тестами добавлена строка «Внимание».
  Результат, выбранный вручную без победителя, коммитится без причины от проверки.

  Фронтенд, не знающий диалог, показывает его как обычный `choice`, которым он и является (§7). Интерфейс ядра без
  `ask_decision` получает тот же вопрос через `ask_choice` с теми же вариантами.
- **Конфликт** останавливает принятие: победитель менял путь, который человек менял после старта прогона, либо его
  патч не ложится на текущий коммит человека. Ничего не меняется; `bestof_finished` — `pending`, а `final` называет
  пути, цитирует текст самого git и говорит, что делать (закоммитить или спрятать правки в этих местах и выполнить
  `/best-of accept <id>`). `command_result` — `ok:false`.
- **`message` в `bestof_finished` и весь `final`** — на языке запроса (не `English / Русский`): `final` всегда несёт
  таблицу вердикта и итог, поэтому фронтенд без экрана best-of показывает этот текст и больше ничего.
  `command_result.message`, как у любой команды, — `English / Русский`.
- **Прогон, оставленный в ожидании** (`pending`, `cancelled`, а также `interrupted`, если умер процесс-владелец)
  управляется тем же словом команды; каждая из них тоже ход, и её события журналируются: `/best-of status`
  (состояние, задача, что оставил каждый исполнитель, вердикт; событий нет), `/best-of diff [id]` (событие
  `bestof_diff` и патч в `final`; без id — победитель), `/best-of accept [id]` (как `accept` выше; без id — победитель,
  а без выбранного победителя ответ — `ok:false` с просьбой назвать id), `/best-of discard`. Они работают с самым
  новым таким прогоном репозитория рабочей папки; если его нет, `command_result` — `ok:false` с пояснением. Id,
  которого в прогоне нет, — ответ `ok:false`, ничего не меняющий. Задача и вердикт прогона хранятся для этого в
  `.kvist/bestof/<run_id>/decision.json`.
- **Отказы.** Без задачи, с одним `N` или с `N` вне 2–6 ответ — `command_result` `ok:false` (использование или
  диапазон, на обоих языках) и **без хода**: ни событий, ни `turn_end`. Там, где best-of не может стартовать (не
  git-репозиторий, ещё нет коммита, откреплённый HEAD, идущие merge или rebase, нет git), ход сразу заканчивается
  этой причиной в `final`, `command_result` — `ok:false`, и ничего не создаётся.
- **Слова управления и задача.** Запрос, который целиком равен `status` или `discard`, либо `diff` или `accept`
  не больше чем с одним словом (id), читается как команда управления выше, а не как задача. Поэтому задачу, которая
  на самом деле начинается с одного из этих слов, пишут иначе: сначала число исполнителей (`/best-of 4 diff двух
  парсеров`) или начать с другого слова (`/best-of сравни два парсера по diff`).
- **Остановка при открытом диалоге решения** (или прямо перед принятием) закрывает вопрос и оставляет прогон
  `pending`, как закрытый диалог: `bestof_finished` `pending`, `final.outcome` `incomplete`, `command_result`
  `ok:false` с `effects.stopped: true` и `effects.outcome: "pending"`; ничего не коммитится. Открытый диалог
  закрывается событием `input_closed` (`reason: "cancelled"`, тот же `request_id`), и второй диалог тоже; поздний
  ответ на него игнорируется. Остановка после
  коммита его не отменяет.
- **`cancel` или пауза** во время прогона останавливают всех исполнителей (`bestof_status` `stopped`), помечают
  прогон `cancelled`, шлют `bestof_finished` `cancelled`, а ход заканчивается с `final.outcome` `incomplete` и
  `command_result` `ok:false` с `effects.stopped: true`. Сделанное остаётся: `/best-of diff e1` покажет его, а
  `/best-of discard` удалит. Проверка, закончившаяся без вердикта (проверяющий остановился простым текстом; «никто не подошёл» — это вердикт без победителя), оставляет прогон `pending`:
  `bestof_finished` `pending`, `ok:false`, результаты исполнителей — в `final`.
- Ход журналируется как любой ход: `user` с набранным текстом (`/best-of …`), `bestof_started`, шаги проверки,
  `bestof_eliminated`, `bestof_verdict`, `bestof_finished`, `final`, `turn_end`; `bestof_status`, `executor_activity`
  и `bestof_diff` — только вживую. Собственная работа исполнителей лежит в их дочерних сессиях
  (`service.kind: "executor"`, §8a). Проверка — не сообщение сессии: она не оставляет записи в истории сессии и
  чекпойнта, их оставляет только сам ход.
- Как для любой команды, `command` во время хода отклоняется сразу; строка цели встаёт в очередь, как встаёт цель.

**Модель предлагает best-of (`offer_best_of`).** Ввод `/best-of` — один путь; второй — сам основной агент. Когда у
задачи заметно разные решения и неверное обойдётся дорого (ядро архитектуры, публичный интерфейс, миграция
данных), модель спрашивает человека перед первым изменением, один раз за прогон. Без согласия ничего не
стартует. Предложение есть только там, где цикл запускает следующий ход: в `--frontend stdio-multi` и в
классическом терминале (ACP и однократный stdio его не предлагают), в ролях, которые меняют файлы, в git-репозитории,
где best-of может стартовать, в интерактивном прогоне, и не у исполнителя, не в проверке и не в ходе, который не
является собственным сообщением человека (пробуждение, возобновление).

```
>>> {"type": "input_request", "request_id": "…", "kind": "choice", "title": "<причина>\nРежим best-of: запустить 4 попытки решить задачу параллельно, каждую в своей копии проекта, и оставить лучшую по итогам проверки. Твои файлы не меняются, пока ты не примешь результат.\nПримерно в 5 раз дороже обычного прогона: 4 попытки и проверка. Это ≈ $1.50 по средним прошлым ходам этой сессии.", "options": [{"value": "best_of", "label": "Запустить best-of (4)"}, {"value": "go", "label": "Обычный прогон"}], …}
<<< {"request_id": "…", "value": "best_of"}
>>> {"type": "final", "message": "Запускаю best-of: 4 попытки решить твою задачу. Результат дождётся твоего решения.", "outcome": "done", …}
>>> {"type": "turn_end"}
>>> …события хода `best-of`, как выше…
>>> {"type": "turn_end"}
>>> {"type": "command_result", "name": "best-of", "ok": true, …}
```

- **Диалог** — обычный `input_request` с `kind: "choice"` (нового `purpose` и нового события нет): сначала причина
  модели, затем что произойдёт, затем цена, на языке запроса. Цена — «примерно в N + 1 раз дороже обычного
  прогона» (N попыток и проверка). Фраза с `≈` добавляется только когда в сессии есть измеренные ходы (из её
  итогов использования, §7): средняя стоимость хода этой сессии (деньги, если у каждого оплаченного вызова была
  цена, иначе токены), умноженная на N + 1. До второго сообщения сессии есть только кратность. N — это `count`
  модели (от 2 до 6, по умолчанию 4). Ответы — `best_of` и `go`; закрытый или не получивший ответа диалог
  считается `go`.
- **Согласие** завершает ход, который предложил режим, коротким `final` и `turn_end`, ни один файл не тронут.
  Затем ядро само запускает следующий ход, как если бы набрали `/best-of N <задача>`: задача — собственное
  сообщение человека из предлагавшего хода, а не пересказ модели, и ход журналируется с этим набранным текстом.
  Его события, `turn_end` и `command_result` — те же, что у команды `best-of` выше. Сообщение, которое человек
  успел поставить в очередь, выполняется после него.
- **Отказ** — заметка модели: она делает задачу сама и в этом прогоне больше не предлагает. `command_result` не
  приходит, потому что команда не запускалась.
- Фронтенду ничего нового не нужно: ни сообщения, ни события; прогон без предложения такой же, как раньше.

Команда `session` или `new`, сменившая активную сессию, тоже шлёт событие
`session` перед своим `command_result`, с `closed`/`closed_notice`, если цель
закрыта.

## 8d. Agent Client Protocol (`--acp`)

`kvist --acp` — второй транспорт того же ядра: участник JSON-RPC 2.0, говорящий
по [Agent Client Protocol](https://agentclientprotocol.com/) в stdin/stdout, для
хостов, у которых ACP уже реализован. Собирается и описан он под Zed.

**Ни одно правило NDJSON-контракта выше в этом режиме не действует.** Здесь нет
`hello`, нет `PROTOCOL_VERSION` и нет `TurnEvent`: типы на проводе приходят из
схемы ACP (`session/new`, `session/prompt`, `session/update`, …). `--workspace`
тоже не используется — рабочая папка приходит с `session/new`, а идентификатор
сессии — стабильная функция этой папки и имени сессии, поэтому он переживает
перезапуск. `--login` принимается только вместе с `--acp`: настроить ключи
провайдера в запускающем терминале и завершиться. **Секреты через соединение ACP
не передаются**: ACP запрещает собирать чувствительные данные в form-режиме,
поэтому отсутствующий ключ не запрашивается по проводу, а в ответ идёт название
команды, которую нужно выполнить.

Реализовано это поверх того же `LocalAgent` / `SafeExecutor` / хранилища сессий,
что и любой другой фронтенд. Собственные файлы режима — `acp_frontend.py`
(участник) и `acp_events.py` (события Kvist → обновления ACP); сведение
накопленных снимков Kvist к дописываемым дельтам ACP живёт во втором.

Возможности заявляются только там, где путь работает до конца: ни NES, ни
MCP-серверов, ни аудио- и image-промптов. Что конкретный хост может и чего не
может показать, записано по каждой возможности в
[`frontends/zed/README.ru.md`](../frontends/zed/README.ru.md) ([EN](../frontends/zed/README.md)).

## 8e. Связь с треем

`frontends/tray` — резидентная иконка для каждого ядра, живущего в терминале. Ядро подключается к ней через `kernel/tray/tray_link.py`; обратно в ядро ничего не приходит. Это не поток событий из §8.

- **Обнаружение.** Демон пишет `~/.kvist/tray.json` (`{"port", "token", "pid"}`, права 0600) и слушает `127.0.0.1:<port>`. Ядро, которому демон недоступен, один раз за процесс запускает его (`KVIST_TRAY_CMD` — JSON-массив argv, либо `frontends/tray/node_modules/electron` из исходников) с `KVIST_CORE_CMD`, равным его собственной команде.
- **Формат.** NDJSON. Первая строка — `{"type": "hello", "token": "..."}`; неверный токен закрывает соединение. Дальше по одному `{"type": "state", "pid", "workspace", "session", "state"}` на каждое изменение, где `state` — `running` (ход начался) или `done` (закончился). Каждое сообщение — полный снимок, поэтому отправитель вправе отбросить все, кроме последнего.
- **Кто отправляет.** Только терминальные ядра: `main()` ставит `KVIST_TRAY_HOST=1` до запуска терминальных фронтендов, ядро Ink-приложения наследует его. Ядра, запущенные GUI, ACP или `run_task.py`, ничего не отправляют.
- **Переключатель.** `tray_enabled` в `~/.kvist/config.json` (отсутствие значит «включено») читается перед каждой отправкой; `kvist --tray-op enable|disable|status` печатает `{"ok", "enabled"}` и завершается.
- **Клиенты бара.** Hello с `"role": "bar"` подписывает на строки `{"type": "summary", "state": "idle|running|done", "count", "tooltip"}` (сразу и при каждом изменении) и позволяет отправить `{"type": "toggle"}`, чтобы открыть или закрыть панель. `kernel/tray/tray_bar.py` добавляет в конфиг Waybar или Polybar пользователя модуль, который запускает `--tray-op bar-stream` и `--tray-op toggle`; правка идемпотентна и сохраняет `<файл>.kvist-backup`.
- **Чтение.** Демон не читает файлы сессий; мини-чат вызывает `--session-op history`.

## 8f. Скиллы, экран Kvist, пауза и помощницы

Скиллы (устанавливаемые пакеты, см. [SKILLS.ru.md](SKILLS.ru.md)) доходят до фронтенда
через дополняющие события `skill`, `screen`, `helper`, `artifact` и `task_state` (§7).
Фронтенд, который их игнорирует, продолжает работать.

**Входящие управляющие сообщения** (`--frontend stdio`, `stdio-multi`; один JSON-объект на строку):

| Сообщение | Действие |
|---|---|
| `{"type": "cancel"}` | **Остановить всё.** Отменяет ход, помощниц и все ресурсы задачи (процессы, runner, виртуальные экраны, порты). Checkpoint сохраняется, поэтому `resume` продолжает. |
| `{"type": "pause"}` | **Пауза.** Kvist и все её помощницы останавливаются в ближайшей безопасной точке. `task_state` идёт `pause_requested` → `paused`; ход заканчивается `final` с `paused: true`, затем `turn_end`. Задача сохраняет dev-сервер, виртуальный экран и помощниц; следующее сообщение человека продолжает ту же задачу. |
| `{"type": "helper_stop", "agent_id": str}` | Останавливает одну помощницу. Kvist узнаёт об этом и сама её не перезапускает; помощница, остановленная человеком, остаётся остановленной, пока человек не напишет снова. Неизвестный id приходит событием `error`. |

Фронтенды привязывают Escape к паузе, а Ctrl+C (или отдельную кнопку «Остановить всё»)
к отмене. Запрос паузы, когда ничего не выполняется, ничего не делает.

**Превью.** Адреса события `screen` ведут на loopback-просмотрщик ядра. Правила для
фронтендов: показывайте `stream_url` в `<img>` (или `frame_url` по таймеру), давайте человеку
открыть `url` в системном браузере, никогда не загружайте эти адреса в страницу, которая может
исполнять другое содержимое, и добавьте `img-src http://127.0.0.1:*` (и то же для `frame-src`,
если встраиваете `url`) в content security policy. Прячьте превью, когда `state` — `closed`.

**Операции управления (без интерфейса, затем выход; JSON в stdout, если это не терминал или
указан `--json`; на терминале `--skill-op` печатает оформленный вид):**
`--skill-op list|show|install|approve|revoke|install-deps|rollback|uninstall|remove-version|reset-data|check`
(с `--skill`, `--skill-path`, `--skill-version`, `--yes`),
`--memory-op status|list|search|get|explain|remember|update|forget|link|pause|resume` (данные в
`--memory-payload` или через stdin; отказ несёт `code`: `privacy`, `permission`, `conflict`, …),
`--mcp-op list|add|remove` и `--connection-op list|add|remove` (секреты через stdin, никогда в
argv). Подробности и смысл — в [SKILLS.ru.md](SKILLS.ru.md).

## 8g. Ядро на сервере (`--remote`)

Ядро может работать на другой машине демоном, который переживает свои фронтенды (см. [remote.ru.md](remote.ru.md)).
Для фронтенда ничего не меняется: вместо локального ядра он запускает `kvist-core --remote HOST
--remote-workspace PATH` и говорит с ним тем же протоколом `--frontend stdio-multi`. Эта программа — прокси:
она держит одно ssh-соединение с демоном, повторяет журнал событий демона фронтенду, который стартует с нуля,
и после обрыва продолжает с того места, где остановилась. От неё приходят два дополнительных события;
фронтенд, который их игнорирует, работает, но не может показать, кому можно писать.

| Событие | Смысл |
|---|---|
| `{"type": "control", "role": "driver"\|"observer", "notice": str, "holder_idle_seconds"?: float}` | Кто может писать в сессию. Ровно один подключённый фронтенд — **водитель**, остальные — **наблюдатели**: они видят всё, а ядро отбрасывает то, что они шлют (цели, команды, ответы на диалоги, `cancel`, `pause`, `helper_stop`). `notice` — текст баннера, который наблюдатель показывает **на месте поля ввода** (кончается на «· Enter — перехватить управление»); своих слов для него у фронтенда нет. Приходит после `hello` и `manifest` и снова при каждой смене роли. |
| `{"type": "remote_state", "state": "connecting"\|"connected"\|"reconnecting"\|"gave_up", "host": str, "reason"?: str, "attempt"?: int, "retry_in"?: float}` | Связь с сервером, от прокси. Пока `reconnecting`, отправить ничего нельзя (строка, написанная в это время, получает ответ: команда — неудачный `command_result`, запрос — `notice` и `turn_end`); вместо поля ввода показывайте `reason` и отсчёт. `gave_up` окончателен: прокси завершается (код 75) с причиной, уже на языке человека. До первого `hello` событий слать нельзя, и прокси пишет те же слова в stderr. |

| Входящее сообщение | Действие |
|---|---|
| `{"type": "takeover"}` | Попросить роль водителя. Прежний водитель сразу становится наблюдателем и узнаёт об этом из `control`. Диалоги (`input_request`), которые ещё открыты, отправляются новому водителю заново с тем же `request_id`; фронтенд обязан считать повтор тем же диалогом. |

`hello` несёт `workspace` (папка ядра, абсолютный путь на машине, где оно работает); для ядра на сервере прокси добавляет `location`:
`<имя машины>:<этот путь>`. Фронтенд, который показывает, где он работает, показывает `location`, если оно есть, а не свою папку-заглушку;
так делают терминальные интерфейсы, которые показывали папку (скин Claude у Ink, OpenCode, Classic), остальные не менялись.

Наблюдатель не отвечает на диалоги и не рисует их: они принадлежат водителю. Водитель, который замолчал (от его
прокси нет пинга 20 с, например при отключении питания), теряет роль; следующий фронтенд берёт её по запросу.

**`/machines` и `/remote` — обычные команды.** Всё, что ядру нужно узнать, оно спрашивает обычными `input_request`
(`choice`, `text`, `secret`, `confirm`), поэтому каждый фронтенд рисует диалог своими виджетами, и ничего не спрашивается на терминале
за его спиной. Эти команды про сохранённые машины и ssh этого компьютера, поэтому для фронтенда на сервере их отвечает сам прокси
(ядро сервера их не видит). Когда человек решил, `command_result` несёт
`effects.relaunch = {switch, label, machine, host, folder, session}`: **фронтенд завершается, чтобы лаунчер запустил его снова там,
куда указал человек.** Фронтенд под лаунчером (Ink, OpenCode, Glass, Voice) пишет `KVIST_SWITCH_FILE` как
`<свой id>\n\n<switch>` и выходит с кодом 64; панель VS Code сохраняет `machine`/`host`/`folder` в настройках и перезапускает своё ядро;
фронтенд, который так не умеет (JetBrains, пиксельное приложение, Electron, ACP), показывает сообщение команды, где сказано, как запустить Kvist там.
`switch` — это `@local`, `@machine<TAB>имя<TAB>папка<TAB>сессия` или `host<TAB>папка`; фронтенд передаёт его как есть.

**Сохранённые машины.** `--machine ИМЯ` — машина, сохранённая через `--machines` (адрес, ключ, папка); фронтенд, который
запускает ядро, передаёт флаги лаунчера дальше, больше ничего не меняется. `--open-session ИМЯ` просит прокси переключить
демон на эту сессию, когда он станет водителем и журнал будет прочитан; если не получится, фронтенд получит событие `error`.
Прокси ещё узнаёт, какая сессия на экране (`hello`, `session`, `session_title`, `turn_end`), и хранит сессии, в которых
был ход, в файле сохранённых машин.

**Операции на сервере** (`--remote-op probe|status|start|stop|install-service|uninstall-service|mkdir`, JSON одной
строкой, а с `--remote HOST --remote-workspace PATH` — через ssh). `--session-op` и `--memory-op` вместе с
`--remote` тоже выполняются на сервере, как и `--config-op`, `--config-info`, `--skill-op`, `--mcp-op` и
`--connection-op`: списки сессий, история и настройки — серверные. Всё, что login-оболочка сервера печатает перед JSON, отбрасывается.

## 9. Универсальный диспетчер фронтендов (`frontends.py`)

Все не-терминальные фронтенды имеют одинаковую склейку (`FrontendChannel` →
`EventStreamUI` → `SafeExecutor(approvals=EventApprovalGate)` → `build_agent(ui=…)` →
`EventSession`), поэтому `frontends.py` строит сессию один раз и отдаёт её
**лаунчеру** — любому callable `launch(session)`.

- Встроенный: `stdio`.
- **Добавить фронтенд = один файл, без правки ядра.** Создайте
  `kvist_frontends/<name>.py` с `def launch(session): …` и запустите
  `kvist --frontend <name>`. Модуль импортируется **лениво** (тяжёлый тулкит вроде
  Qt/aiohttp грузится только при выборе).

Лаунчер получает готовый `EventSession` и управляет им:

```python
def launch(session):
    session.submit(goal)                 # старт прогона (worker-поток)
    for event in session.events():       # блокируется/поллит до конца прогона
        data = event.to_dict()
        if data["type"] == "input_request":
            session.respond(data["request_id"], value=...)      # или approved=True/False
        else:
            render(data)
    session.close()
```

API `EventSession`: `submit(user_goal, routed_role=None)`, `submit_resume()`
(продолжить checkpoint активной сессии), `events()` (итератор; заканчивается,
когда worker завершился и очередь пуста), `respond(request_id, *, value=None,
approved=None)`, `close(timeout=5.0)`, `is_running()`.

## 10. Другой язык (Electron / JS / что угодно)

JSON-граница означает, что «красота» может быть на любом языке, а Python-ядро работает
как **дочерний процесс** — классический паттерн «движок за stdio-RPC» (как LSP/DAP/git).
Ваше приложение не импортирует Python — только говорит на JSON из §7–§8.

```javascript
const { spawn } = require("child_process");
const readline = require("readline");

const proc = spawn("kvist", ["--workspace", ws, "--frontend", "stdio"]);
proc.stdin.write("do the thing\n");                 // задача = первая строка stdin
readline.createInterface({ input: proc.stdout }).on("line", (line) => {
  const ev = JSON.parse(line);
  switch (ev.type) {
    case "hello":            checkVersion(ev.protocol_version);        break;
    case "stream_chunk":     appendStreaming(ev.stream_id, ev.text);   break;  // эффект живого набора
    case "reasoning_start":  showThinking(ev.stream_id);               break;  // модель думает
    case "reasoning_chunk":  updateThinking(ev.stream_id, ev.text);    break;  // серые живые мысли
    case "reasoning_commit": collapseThinking(ev.stream_id, ev.duration_seconds); break; // «Thought for Ns»
    case "status":           showStatus(ev);                           break;
    case "final":        showFinal(ev.message);             break;
    case "error":        showError(ev.message);             break;
    case "input_request":
      askUser(ev).then((answer) => {
        const reply = ev.kind === "confirm"
          ? { request_id: ev.request_id, approved: answer }
          : { request_id: ev.request_id, value: answer };
        proc.stdin.write(JSON.stringify(reply) + "\n");
      });
      break;
    // default: игнорировать неизвестные типы событий (forward-compat)
  }
});
```

**Дистрибуция:** соберите ядро в замороженный бинарь (`kvist.spec` / PyInstaller) и
положите внутрь приложения — тогда конечным пользователям Python не нужен вообще.
Electron просто спавнит бинарь `kvist`.

**Браузер (не Electron):** stdio не подходит; напишите socket/websocket-лаунчер
(`kvist_frontends/websocket.py`), который качает тот же `FrontendChannel` через сокет.
Ядро не меняется — только транспорт.

## 11. Заметки, ограничения и гарантии (v1)

- **Креды.** `build_agent` резолвит креды провайдера заранее (из
  `~/.kvist/config.json`); headless-фронтенду они нужны **заранее настроенными**. Ввод
  кредов через события пока не подключён — настройте провайдера один раз через терминал
  или поставьте конфиг. Если провайдер/модель отсутствуют и нет TTY, ядро завершается с
  ненулевым кодом и сообщением в stderr (fail-closed).
- **Подтверждения fail-closed.** Без внедрённого gate — терминальные запросы; через
  события закрытый/молчащий фронтенд отклоняет опасные команды. `--approval-mode deny`
  отклоняет все запросы подтверждения без показа диалога.
- **Цикл агента не менялся.** Фронтенды не вызывают внутренности агента — только
  рендерят события и отвечают на запросы.
- **Терминал — особый дефолт.** Его REPL добавляет slash-команды и визарды
  конфигурации сверх событийной поверхности. Управление же жизненным циклом
  сессий полностью доступно headless-фронтендам через `--session-op` и
  `--resume` (§8a) — с той же семантикой, что и терминальные команды. Под
  `stdio-multi` основные слэш-команды выполняются и в процессе ядра (§8c).
- **Один процесс = один прогон** в v1. Прогон выполняется в активной
  именованной сессии workspace; между прогонами сессии переключаются через
  `--session-op switch`. Для нескольких одновременных клиентов — процесс на
  workspace или мультиплексирующий socket-транспорт. Само хранилище сессий
  безопасно при конкурирующих записях (per-path блокировки + атомарная замена),
  но одновременная работа двух агентов в одном workspace не поддерживается.

## 8h. Список провайдеров: `--config-info`

`kvist --workspace WS --config-info` печатает один JSON-объект со всеми провайдерами (`providers`, затем
`custom_providers`): `id`, `label`, `auth_type`, `has_credentials`, `defaults`, `saved_models` и `options`
(модели, которые он предлагает, каждая `{value, label, description, icon}`). Для фронтенда, который рисует
логотипы, `icon` называет бренд коротким slug (`anthropic`, `openai`, ...; у своего провайдера пусто), а
`model_icons` сопоставляет каждому упомянутому моделью id бренд её производителя, так что `cc/claude-opus-5`
через шлюз показывает знак Anthropic. Slug'и берутся из `kernel/config/brand_icons.py`; фронтенд без картинки
для slug'а рисует монограмму.
