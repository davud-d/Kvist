# Kvist Cloud

*(English version: [README.md](README.md))*

Подписка, где у каждого клиента своя облачная машина с Kvist. Клиент вставляет свой ключ модели,
пишет задачу, агент выполняет её на машине. Между задачами машина спит; клиент платит за часы, пока
агент работает.

В этой папке MVP: сервер управления, раннер, который живёт на каждой машине, и веб-фронтенд. Всё
работает на одном компьютере; на сервере машина каждого клиента — виртуальная машина KVM, которую создаёт
`backend/kvist_cloud/providers/libvirt.py` ([docs/DEPLOY.ru.md](docs/DEPLOY.ru.md)). Устройство описано в
[docs/ARCHITECTURE.ru.md](docs/ARCHITECTURE.ru.md).

## Запуск локально

```bash
./cloud/scripts/dev.sh
```

Затем открой <http://127.0.0.1:8740>. Скрипт создаёт `cloud/.venv`, собирает фронтенд, один раз
генерирует локальные секреты (в `cloud/.cloud-data/dev-secrets.env`, права 0600, никогда не
печатаются), запускает фейковую модель на порту 8799 и сервер на порту 8740.

* **Вход:** без настроенного GitHub-приложения кнопка входит локальным пользователем `dev`
  (`AUTH_DEV_LOGIN`, только на loopback). Для настоящего входа создай GitHub OAuth App с callback URL
  `http://127.0.0.1:8740/auth/github/callback` и запиши `GITHUB_CLIENT_ID` и `GITHUB_CLIENT_SECRET`
  в `cloud/.env`. При другом `PORT` укажи соответствующий порт в callback URL. Секрет не коммить.
  Для опубликованного сервера используй `<PUBLIC_URL>/auth/github/callback` и HTTPS.
  Пробный период для настоящего GitHub-аккаунта доступен один раз и только строго спустя календарный месяц.
* **Карта:** биллинг выключен, пока `cloud/.env` не скажет `BILLING_ENABLED=true` (см. «Оплата» ниже). Пока
  выключен, шаг оплаты — заглушка: нажми «Пропустить (dev)». Больше ничего передавать не нужно: ни флагов, ни переменных.
* **Модель:** выбери «Другой», base URL `http://127.0.0.1:8799/v1`, модель `fake-model`, любой
  ключ от 8 символов. Фейковая модель проигрывает короткий сценарий через **настоящее ядро Kvist**:
  записывает `CLOUD_NOTES.md`, читает его и отвечает. Ничего не уходит с компьютера.
* **Админка:** <http://127.0.0.1:8740/admin> — админ-панель: люди (тарифы, часы, права админа, остановка машины, баны), конверсия воронки и открытые споры.

Если ядро не установлено, `dev.sh` сам берёт сценарную заглушку Kvist
(`runner/tests/fake_kvist.py`); `--fake-kvist` включает её принудительно — чтобы работать над интерфейсом без окружения ядра.

Настоящее ядро запускается из собственного `.venv` репозитория (`python -m kernel`). Если его нет:

```bash
python3 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt
```

Нужны Python 3.11+, Node 20+, git. Для лимитов CPU и памяти машины используется
`systemd-run --user`, если он работает; без него раннер пишет предупреждение в лог и работает без
лимитов.

## Настройка

Только переменные окружения. Обязательные:

| Переменная | Что это |
| --- | --- |
| `KVIST_CLOUD_SESSION_SECRET` | подпись cookie сессий, от 32 символов |
| `KVIST_CLOUD_MASTER_KEY` | ключ(и) Fernet для ключей моделей в базе; через запятую для ротации, первый шифрует |
| `PUBLIC_URL` | собственный адрес сервера (`https://…` включает secure-cookie) |

Необязательные: `DATABASE_URL` (по умолчанию SQLite в `KVIST_CLOUD_DATA_DIR`), `GITHUB_CLIENT_ID` /
`GITHUB_CLIENT_SECRET`, `BILLING_ENABLED` вместе с переменными `PLATEGA_*` ниже;
`MACHINE_PROVIDER` (`local`), `KVIST_COMMAND`, `RUNNER_COMMAND`, `HEARTBEAT_SECONDS` (15),
`HEARTBEAT_MAX_GAP_SECONDS` (45), `MACHINE_IDLE_SLEEP_SECONDS` (900), `PROVIDER_OUTAGE_SECONDS`
(300), `HOURS_GRACE_SECONDS` (300), `ADMIN_GITHUB_LOGINS` и только для разработки
`AUTH_DEV_LOGIN`, `ALLOW_LOCAL_ENDPOINTS` (обе запрещены, если `PUBLIC_URL` не loopback).

### Оплата (Platega)

Переменные берутся из окружения процесса и, ниже приоритетом, из файла `cloud/.env` (или из файла,
который назван в `KVIST_CLOUD_ENV_FILE`). Скопируй `cloud/env.example` в `cloud/.env`, заполни и не
коммить: `.env` лежит в `.gitignore`. Настоящая переменная окружения сильнее файла.

| Переменная | Что это |
| --- | --- |
| `BILLING_ENABLED` | `true` включает оплату; тогда нужно всё ниже, кроме необязательного |
| `PLATEGA_MERCHANT_ID` | UUID мерчанта (`X-MerchantId`, кабинет Platega: Настройки) |
| `PLATEGA_SECRET` | API-ключ (`X-Secret`), только на сервере |
| `PLATEGA_PRICE_START` / `_PRO` / `_MAX` / `_HOURS` / `_REMOTE` | цена каждой покупки, например `1500.00`; `_REMOTE` — цена целого года |
| `PLATEGA_CURRENCY` | необязательно, по умолчанию `RUB` |
| `PLATEGA_PAYMENT_METHODS` | необязательно, через запятую, в порядке показа; по умолчанию `2,11,12,13` (СБП, карты, международная, крипта); ещё `3` ЕРИП, `14` Sberpay |
| `PLATEGA_BASE_URL` | необязательно, по умолчанию `https://app.platega.io` |

Callback URL (кабинет: Настройки → Callback URLs) — `<PUBLIC_URL>/billing/platega/callback`; нужен
публичный HTTPS.

**Чему верит backend.** Platega ничего не подписывает: в callback только два статических заголовка.
Поэтому сервер считает его звонком в дверь. Он сверяет заголовки (за постоянное время), берёт из тела
*только* id транзакции и сам спрашивает Platega (`GET /transaction/{id}` с нашими ключами) статус,
сумму и валюту. Тариф или часы выдаются, только если эта запись относится к строке `billing_checkouts`,
которую наш сервер создал для вошедшего пользователя, статус `CONFIRMED`, а сумма, валюта и payload
точно совпадают со строкой. Суммы берутся из настроек сервера; браузер присылает лишь название тарифа
и не определяет ни цену, ни адрес возврата, ни пользователя. Обработка идемпотентна (checkout
оплачивается один раз при любом порядке дублей), платёж, который нельзя применить или который не
совпал, помечается `mismatch` / `needs_review` и пишется в лог вместо начисления, а `CANCELED` /
`CHARGEBACKED` (перепроверенные у Platega) забирают часы или завершают тариф. Если callback не пришёл,
платёж так же находит вызов страницы «проверить оплату» (`POST /api/billing/sync`) и фоновый проход раз
в пять минут.

Что следует из модели Platega, а не из наших решений:

- Платежи разовые. Тариф действует 30 дней и **сам не продлевается**: человек платит снова (кнопка
  «Продлить» появляется за 3 дня до конца, новый месяц начинается, когда кончается этот).
- Пробный период бесплатный и без карты (проверки карты в Platega нет). Один на аккаунт, для
  GitHub-аккаунтов старше месяца. Оплата заменяет идущий пробный период.
- Callback-и `PARTIALLY_REFUNDED` и `DISPUTED` нельзя проверить через эндпоинт статуса, поэтому они
  ничего не меняют; разбирай их вручную в кабинете Platega и в ledger.
- Списывается `PLATEGA_CURRENCY`; доллары в таблице тарифов — только каталог.

### Фото в сообщениях

В сообщении могут быть фото (конверт `kvist-image-goal` из `docs/vision.md`, тот же, что у других интерфейсов). Специально
сделанная картинка — это атака на парсер, а сервер управления хранит секреты всех клиентов, поэтому он никогда не декодирует
пиксели: [`images.py`](backend/kvist_cloud/images.py) читает *структуру* PNG или JPEG, проверяет каждую длину и контрольную сумму,
распаковывает данные PNG ограниченными порциями до точного размера, обещанного заголовком (бомба отклоняется и не держится в
памяти), выбрасывает текст, EXIF, профили ICC, анимацию и всё, что идёт после конца файла (полиглот теряет вторую жизнь), и
записывает картинку заново. Только PNG и JPEG, по байтам, а не по заявленному типу; не больше 8 фото, по 5 МБ, 20 МБ вместе,
25 мегапикселей. Конверт распознаётся по правилу самого ядра (JSON, любые пробелы и порядок ключей), поэтому другая запись
конверта не обходит проверку. История хранит имена фото, а не пиксели (фото первого сообщения ждут в `tasks.start_envelope`).
Страница ещё и сжимает каждое фото до JPEG не больше 2048 px перед отправкой: так поворот камеры запекается в пиксели, а метаданные
исчезают у источника; серверу это не нужно, он не доверяет. Ядро Kvist на машине всё равно декодирует переписанный файл своей
библиотекой: это собственная машина клиента, и файл, который оно получает, проще исходного.

### Freedom Pay (freedompay.kg)

**Страница оплаты** Freedom Pay, Merchant API из [docs.freedompay.kz](https://docs.freedompay.kz) (хост `.kg` обслуживает Кыргызстан).
Выключено, пока нет `FREEDOMPAY_ENABLED=true` (переменные в `env.example`; merchant id и платёжный секретный ключ — в личном
кабинете). Страница для телефона показывает её среди «другим способом»; человек платит в системном браузере, где Freedom Pay показывает
свои карты и, если у мерчанта подключены, **Apple Pay и Google Pay**. Их документация не описывает способ передать токен кошелька на
сервер мерчанта, кроме Gateway API с PCI DSS, а запрос с токеном кошелька в прочитанном нет: поэтому собственные окна кошельков в
приложениях (ниже) остаются на Stripe, а у менеджера Freedom Pay стоит спросить, предполагается ли их использовать с ним.

Правило то же, что у Platega, но «звонок» надёжнее: покупка — строка `BillingCheckout`, которую создал сервер
(`POST /api/freedompay/checkout`, цена из `FREEDOMPAY_PRICE_*`); callback `POST /billing/freedompay/result` несёт подпись MD5 от имени
скрипта, отсортированных значений и секретного ключа и засчитывается, только если подпись верна, а заказ, id платежа, сумма и валюта —
из строки; отвечаем `ok` в любом случае. Callback, который не пришёл, восполняется `get_status3.php`, когда человек возвращается
(`POST /api/billing/sync`). Не сделано: возвраты и чарджбэки (вручную в кабинете и в ledger) и фоновая проверка. Тесты используют
`backend/tests/freedompay_fake.py`, построенный по документации: они не проверяют настройки аккаунта, адрес callback
(`<PUBLIC_URL>/billing/freedompay/result`, его нужно передать менеджеру) и то, в какой валюте может списывать мерчант из Кыргызстана.

### Apple Pay и Google Pay (Stripe)

Приложения открывают встроенное платёжное окно операционной системы; деньги идут через Stripe, потому что токен кошелька может
списать только процессор, который его принимает (в документации Platega такого способа нет). Выключено, пока нет
`WALLET_ENABLED=true` (переменные в `env.example`); Platega остаётся для всего остального. Цены по умолчанию берутся из таблицы
тарифов в USD (`WALLET_PRICE_*`).

1. Панель Stripe: ключи API (`STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`; тестовый и боевой ключ смешивать нельзя) и
   webhook `<PUBLIC_URL>/billing/stripe/webhook` на события `payment_intent.succeeded`, `charge.refunded` и
   `charge.dispute.created` (его секрет подписи — `STRIPE_WEBHOOK_SECRET`).
2. Для Google Pay в режиме `TEST` ничего не нужно; для боя см. `frontends/cloud-android/README.ru.md`. Для Apple Pay нужны Merchant ID
   и его сертификат, загруженный в Stripe: `frontends/cloud-ios/README.ru.md`.

**Чему верит бэкенд.** То же правило, что и для Platega, но с более сильным «звонком в дверь». Покупка существует только как строка
`BillingCheckout`, которую создал сервер (`POST /api/wallet/checkout`, цена — серверная); телефон возвращает токен кошелька
(`POST /api/wallet/pay`), сервер превращает его в токен Stripe (у Google он уже такой; токен Apple уходит в `POST /v1/tokens`), создаёт
и подтверждает PaymentIntent с ключом идемпотентности из оплаты и засчитывает покупку, только если ответ самого Stripe — `succeeded`
ровно на эту сумму, валюту и токен оплаты. Webhook Stripe подписан, но тоже служит лишь поводом ещё раз посмотреть PaymentIntent
(так засчитывается платёж, если приложение закрыли после оплаты); полный возврат или спор забирает покупку обратно. Карта, которой
нужен дополнительный шаг банка, не может пройти его в окне кошелька: PaymentIntent отменяется, а человеку предлагают оплатить другим
способом.

Не проверено на самом Stripe (здесь нет ключей; тесты используют `backend/tests/stripe_fake.py`): что Stripe принимает токен Apple Pay
в `POST /v1/tokens` с `pk_token` так, как его отправляет iOS-библиотека, и точное поведение аккаунта с `allow_redirects=never`.
Перед включением проведи один платёж в тестовом режиме с телефона.

### Remote: собственная машина клиента

Четвёртый тариф для тех, у кого уже есть компьютер: **$48 в год, один платёж, без ежемесячных
списаний** (`PLATEGA_PRICE_REMOTE`, в вашей валюте). Агент работает там, а не на нашей машине, поэтому
часы не считаются и пакеты часов не продаются. Облако выступает посредником: машина клиента сама
открывает соединение к нам, а остальное (задачи, очередь, веб-рабочее место, история) работает как у
любого тарифа.

Как подключается: после оплаты кнопка «Подключить мою машину» на панели создаёт запись машины и **один
раз** показывает `runner.json` (`machine_id`, `gateway_url`, токен); токен хранится только как хеш.
Клиент сохраняет его на компьютере с Kvist и запускает `kvist-runner --config runner.json`: тот
дозванивается до `/gateway/ws`, как runner на наших машинах. Мы не получаем ssh-ключ или пароль и не
ходим на адрес, который ввёл клиент (иначе сервер стал бы сканером). Повторное нажатие кнопки выпускает
новый токен и разрывает старое соединение, так что утёкший конфиг лечится повторным нажатием. Выключенная
машина показывается как «не в сети», от неё не отказываются; задачи ждут. Runner не ставит лимиты CPU и
памяти на собственный компьютер владельца.

Пока не сделано: способ поставить `kvist-runner` на чужой компьютер (опубликованного пакета нет) и
очистка пробной машины на нашей стороне при переходе на Remote (её не трогают и скрывают).

Миграция `0006` удаляет таблицы Paddle (он работал только в sandbox) и колонки Paddle в
`subscriptions`; обратить её нельзя. Перед live-оплатой сделай настоящий тестовый платёж на своём
мерчанте: тесты в репозитории используют заглушку по опубликованному API Platega и не проверят
настройки кабинета, callback URL и то, что Platega возвращает `payload` в ответе статуса (проверка
терпит его отсутствие, но отвергает другое значение).

Документация провайдера: [Platega API](https://docs.platega.io/),
[GitHub OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps).

Возраст берётся из `created_at`, полученного от GitHub после OAuth: аккаунт должен быть строго
старше календарного месяца. Trial доступен один раз; неизвестный возраст запрещает его до
повторного входа. Dev-оплата, бесплатные часы и искусственные продления работают только при
`AUTH_DEV_LOGIN=true`, выключенном биллинге и loopback `PUBLIC_URL`.
`MACHINE_PROVIDER=local` ограничен loopback: он **не изолирует** недоверенных пользователей.
`MACHINE_PROVIDER=libvirt` изолирует: на клиента одна виртуальная машина KVM, сеть изолирована так, как описано
в [docs/DEPLOY.ru.md](docs/DEPLOY.ru.md).

OAuth запрашивает `read:user repo`. Для приватных репозиториев существующим пользователям
нужно переподключить GitHub и разрешить `repo`, а при необходимости — доступ организации.
Scope `repo` широкий. Токен зашифрован в базе; при клонировании передаётся через Git-заголовок,
ограниченный github.com, не попадает в URL remote или окружение агента. Принимаются только
GitHub HTTPS URL; локальные file URL разрешены лишь в dev-режиме. Авторизованные fetch/push
из агента эта интеграция клонирования не предоставляет; экспорт архива сохранён.

### Обновление на месте

Машина клиента — тонкий слой над образом диска, с которого она создана, и без этого оставалась бы на том Kvist, с
которым родилась. Вместо этого сервер подтягивает её до колёс из `WHEELS_DIR` (по умолчанию
`/opt/kvist-cloud/wheels`; `UPDATE_IDLE_SECONDS`, по умолчанию 1800) без нового образа
(`backend/kvist_cloud/updates.py`, `runner/kvist_runner/release.py`):

- Машине, которую никто не трогал 30 минут (спящую будим, не больше двух за 30 с), велено подготовить релиз: раннер
  скачивает два колеса своим токеном, сверяет контрольные суммы, распаковывает их в `releases/<id>/site` рядом с
  работающим кодом и проверяет, что Kvist и раннер импортируются оттуда.
- Подготовка не трогает запущенную задачу. Кто вернулся в это время, работает на старом Kvist.
- Когда всё готово, раннер останавливает каждый запущенный Kvist (через 5 с убивает; сессия уже на диске), переводит
  `current-release` на новый релиз и перезапускает сам себя. Каждая остановленная задача сообщает `core_updated`, и
  сервер продолжает её в той же сессии на новом Kvist, как только раннер снова скажет hello.
- «Машина обновляется» решает только сервер и только в ответ на посланный им `update`; чужой `update_ready` или
  `core_updated` без запроса игнорируется или становится обычной паузой. Страница читает `updating` из
  `GET /api/machines`; ни один маршрут его не задаёт.
- Клиенту это ничего не стоит: часы списываются только за интервалы, которые назвал heartbeat запущенной задачи, а
  переключаемая задача в статусе `starting`, не `running`. Без часов переключённая задача встаёт на паузу, а не
  продолжается.
- Заменяются только два колеса. Релиз, которому нужна зависимость, которой нет в образе, не проходит проверку
  импорта и не включается; для него нужен новый образ (`scripts/deploy.sh` собирает его, когда колёса изменились).

cd cloud/backend  && ../.venv/bin/python -m pytest && ../.venv/bin/ruff check .
