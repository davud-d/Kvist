# Kvist Cloud

*(English version: [README.md](README.md))*

Подписка, где у каждого клиента своя облачная машина с Kvist. Клиент вставляет свой ключ модели,
пишет задачу, агент выполняет её на машине. Между задачами машина спит; клиент платит за часы, пока
агент работает.

В этой папке MVP: сервер управления, раннер, который живёт на каждой машине, и веб-фронтенд. Всё
работает на одном компьютере; для запуска на настоящем хостинге остаётся написать один адаптер
провайдера (`backend/kvist_cloud/providers/sprites.py`). Устройство описано в
[docs/ARCHITECTURE.ru.md](docs/ARCHITECTURE.ru.md).

## Запуск локально

```bash
./cloud/scripts/dev.sh
```

Затем открой <http://127.0.0.1:8740>. Скрипт создаёт `cloud/.venv`, собирает фронтенд, один раз
генерирует локальные секреты (в `cloud/.cloud-data/dev-secrets.env`, права 0600, никогда не
печатаются), запускает фейковую модель на порту 8799 и сервер на порту 8740.

* **Вход:** кнопка GitHub входит локальным пользователем `dev` (`AUTH_DEV_LOGIN`, только на
  loopback).
* **Карта:** биллинг выключен, поэтому шаг карты — заглушка: нажми «Пропустить (dev)».
* **Модель:** выбери «Другой», base URL `http://127.0.0.1:8799/v1`, модель `fake-model`, любой
  ключ от 8 символов. Фейковая модель проигрывает короткий сценарий через **настоящее ядро Kvist**:
  записывает `CLOUD_NOTES.md`, читает его и отвечает. Ничего не уходит с компьютера.
* **Админка:** <http://127.0.0.1:8740/admin> показывает конверсию воронки и открытые споры.

`./cloud/scripts/dev.sh --fake-kvist` вместо ядра использует сценарную заглушку Kvist
(`runner/tests/fake_kvist.py`) — чтобы работать над интерфейсом без окружения ядра.

Настоящее ядро запускается из собственного `.venv` репозитория (`python -m kernel`). Если его нет:

```bash
python3 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt
```

Нужны Python 3.11+, Node 20+, git. Для лимитов CPU и памяти машины используется
`systemd-run --user`, если он работает; без него раннер пишет предупреждение в лог и работает без
лимитов.

## Настройка

Только переменные окружения. Обязательные:

| Переменная | Что это |
| --- | --- |
| `KVIST_CLOUD_SESSION_SECRET` | подпись cookie сессий, от 32 символов |
| `KVIST_CLOUD_MASTER_KEY` | ключ(и) Fernet для ключей моделей в базе; через запятую для ротации, первый шифрует |
| `PUBLIC_URL` | собственный адрес сервера (`https://…` включает secure-cookie) |

Необязательные: `DATABASE_URL` (по умолчанию SQLite в `KVIST_CLOUD_DATA_DIR`), `GITHUB_CLIENT_ID` /
`GITHUB_CLIENT_SECRET`, `BILLING_ENABLED` вместе с переменными `PLATEGA_*` ниже;
`MACHINE_PROVIDER` (`local`), `KVIST_COMMAND`, `RUNNER_COMMAND`, `HEARTBEAT_SECONDS` (15),
`HEARTBEAT_MAX_GAP_SECONDS` (45), `MACHINE_IDLE_SLEEP_SECONDS` (900), `PROVIDER_OUTAGE_SECONDS`
(300), `HOURS_GRACE_SECONDS` (300), `ADMIN_GITHUB_LOGINS` и только для разработки
`AUTH_DEV_LOGIN`, `ALLOW_LOCAL_ENDPOINTS` (обе запрещены, если `PUBLIC_URL` не loopback).

### Оплата (Platega)

Переменные берутся из окружения процесса и, ниже приоритетом, из файла `cloud/.env` (или из файла,
который назван в `KVIST_CLOUD_ENV_FILE`). Скопируй `cloud/env.example` в `cloud/.env`, заполни и не
коммить: `.env` лежит в `.gitignore`. Настоящая переменная окружения сильнее файла.

| Переменная | Что это |
| --- | --- |
| `BILLING_ENABLED` | `true` включает оплату; тогда нужно всё ниже, кроме необязательного |
| `PLATEGA_MERCHANT_ID` | UUID мерчанта (`X-MerchantId`, кабинет Platega: Настройки) |
| `PLATEGA_SECRET` | API-ключ (`X-Secret`), только на сервере |
| `PLATEGA_PRICE_START` / `_PRO` / `_MAX` / `_HOURS` / `_REMOTE` | цена каждой покупки, например `1500.00`; `_REMOTE` — цена целого года |
| `PLATEGA_CURRENCY` | необязательно, по умолчанию `RUB` |
| `PLATEGA_PAYMENT_METHODS` | необязательно, через запятую, в порядке показа; по умолчанию `2,11,12,13` (СБП, карты, международная, крипта); ещё `3` ЕРИП, `14` Sberpay |
| `PLATEGA_BASE_URL` | необязательно, по умолчанию `https://app.platega.io` |

Callback URL (кабинет: Настройки → Callback URLs) — `<PUBLIC_URL>/billing/platega/callback`; нужен
публичный HTTPS.

**Чему верит backend.** Platega ничего не подписывает: в callback только два статических заголовка.
Поэтому сервер считает его звонком в дверь. Он сверяет заголовки (за постоянное время), берёт из тела
*только* id транзакции и сам спрашивает Platega (`GET /transaction/{id}` с нашими ключами) статус,
сумму и валюту. Тариф или часы выдаются, только если эта запись относится к строке `billing_checkouts`,
которую наш сервер создал для вошедшего пользователя, статус `CONFIRMED`, а сумма, валюта и payload
точно совпадают со строкой. Суммы берутся из настроек сервера; браузер присылает лишь название тарифа
и не определяет ни цену, ни адрес возврата, ни пользователя. Обработка идемпотентна (checkout
оплачивается один раз при любом порядке дублей), платёж, который нельзя применить или который не
совпал, помечается `mismatch` / `needs_review` и пишется в лог вместо начисления, а `CANCELED` /
`CHARGEBACKED` (перепроверенные у Platega) забирают часы или завершают тариф. Если callback не пришёл,
платёж так же находит вызов страницы «проверить оплату» (`POST /api/billing/sync`) и фоновый проход раз
в пять минут.

Что следует из модели Platega, а не из наших решений:

- Платежи разовые. Тариф действует 30 дней и **сам не продлевается**: человек платит снова (кнопка
  «Продлить» появляется за 3 дня до конца, новый месяц начинается, когда кончается этот).
- Пробный период бесплатный и без карты (проверки карты в Platega нет). Один на аккаунт, для
  GitHub-аккаунтов старше месяца. Оплата заменяет идущий пробный период.
- Callback-и `PARTIALLY_REFUNDED` и `DISPUTED` нельзя проверить через эндпоинт статуса, поэтому они
  ничего не меняют; разбирай их вручную в кабинете Platega и в ledger.
- Списывается `PLATEGA_CURRENCY`; доллары в таблице тарифов — только каталог.

### Remote: собственная машина клиента

Четвёртый тариф для тех, у кого уже есть компьютер: **$48 в год, один платёж, без ежемесячных
списаний** (`PLATEGA_PRICE_REMOTE`, в вашей валюте). Агент работает там, а не на нашей машине, поэтому
часы не считаются и пакеты часов не продаются. Облако выступает посредником: машина клиента сама
открывает соединение к нам, а остальное (задачи, очередь, веб-рабочее место, история) работает как у
любого тарифа.

Как подключается: после оплаты кнопка «Подключить мою машину» на панели создаёт запись машины и **один
раз** показывает `runner.json` (`machine_id`, `gateway_url`, токен); токен хранится только как хеш.
Клиент сохраняет его на компьютере с Kvist и запускает `kvist-runner --config runner.json`: тот
дозванивается до `/gateway/ws`, как runner на наших машинах. Мы не получаем ssh-ключ или пароль и не
ходим на адрес, который ввёл клиент (иначе сервер стал бы сканером). Повторное нажатие кнопки выпускает
новый токен и разрывает старое соединение, так что утёкший конфиг лечится повторным нажатием. Выключенная
машина показывается как «не в сети», от неё не отказываются; задачи ждут. Runner не ставит лимиты CPU и
памяти на собственный компьютер владельца.

Пока не сделано: способ поставить `kvist-runner` на чужой компьютер (опубликованного пакета нет) и
очистка пробной машины на нашей стороне при переходе на Remote (её не трогают и скрывают).

Миграция `0006` удаляет таблицы Paddle (он работал только в sandbox) и колонки Paddle в
`subscriptions`; обратить её нельзя. Перед live-оплатой сделай настоящий тестовый платёж на своём
мерчанте: тесты в репозитории используют заглушку по опубликованному API Platega и не проверят
настройки кабинета, callback URL и то, что Platega возвращает `payload` в ответе статуса (проверка
терпит его отсутствие, но отвергает другое значение).

Документация провайдера: [Platega API](https://docs.platega.io/),
[GitHub OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps).

Возраст берётся из `created_at`, полученного от GitHub после OAuth: аккаунт должен быть строго
старше календарного месяца. Trial доступен один раз; неизвестный возраст запрещает его до
повторного входа. Dev-оплата, бесплатные часы и искусственные продления работают только при
`AUTH_DEV_LOGIN=true`, выключенном биллинге и loopback `PUBLIC_URL`.
`MACHINE_PROVIDER=local` ограничен loopback: он **не изолирует** недоверенных пользователей.
Адаптер Sprites ещё не реализован, поэтому публичный хостинг пока не готов.

OAuth запрашивает `read:user repo`. Для приватных репозиториев существующим пользователям
нужно переподключить GitHub и разрешить `repo`, а при необходимости — доступ организации.
Scope `repo` широкий. Токен зашифрован в базе; при клонировании передаётся через Git-заголовок,
ограниченный github.com, не попадает в URL remote или окружение агента. Принимаются только
GitHub HTTPS URL; локальные file URL разрешены лишь в dev-режиме. Авторизованные fetch/push
из агента эта интеграция клонирования не предоставляет; экспорт архива сохранён.

## Проверки

```bash
cd cloud/backend  && ../.venv/bin/python -m pytest && ../.venv/bin/ruff check .
cd cloud/runner   && ../.venv/bin/python -m pytest && ../.venv/bin/ruff check .
cd cloud/frontend && npm test && npm run build
node --test "cloud/pixel/tests/*.test.mjs"      # логика страницы пиксельного окна
./cloud/frontend/tools/lighthouse.sh          # при запущенном dev.sh; METHOD=simulate — модель Lighthouse
```

`backend/tests/test_e2e_local.py` — сквозной тест: настоящий сервер на настоящем порту,
local-провайдер с настоящим раннером, воронка по HTTP, поток задачи через браузерный WebSocket,
проверка списания и воронки. Его вариант `real_core` проходит то же через настоящее ядро Kvist;
без окружения ядра отключи его через `-m "not real_core"`.
