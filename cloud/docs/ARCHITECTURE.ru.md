# Kvist Cloud — архитектура

*(English version: [ARCHITECTURE.md](ARCHITECTURE.md))*

Kvist Cloud — это подписка: у каждого клиента своя облачная машина с Kvist. Клиент вставляет
свой ключ модели, пишет задачу, агент выполняет её на машине. Между задачами машина спит, а
клиент платит за часы активной работы агента.

MVP целиком работает на одном компьютере. Ненастоящим пока остаётся только адаптер хостинга
(`providers/sprites.py`), вместо него работает `providers/local.py`.

## Схема

```
 браузер ──HTTPS + cookie──▶ сервер управления (FastAPI) ◀──WebSocket (исходящий с машины)── раннер
   │  ▲                       │  users, machines, tasks,                                      │
   │  └──WebSocket: события ──┤  task_events, ledger_entries,                                 │ запускает на задачу
   │     задачи               │  subscriptions, funnel_events                                 ▼
   │                          │                                                 kvist --frontend stdio-multi
   │                          ├── providers/<name>: create · wake · sleep · delete · status    (режим B, NDJSON)
   └─страница оплаты Platega   └── billing.py ◀── callback-и Platega (по умолчанию BILLING_ENABLED=false)
```

* **Сервер управления** (`backend/kvist_cloud`) — единственная часть с состоянием. SQLite по
  умолчанию, PostgreSQL через `DATABASE_URL`. Отдаёт API, два WebSocket и собранный фронтенд.
* **Раннер** (`runner/kvist_runner`) — один процесс на машину. Сам подключается к серверу
  (входящих портов у машины нет), шлёт heartbeat каждые 15 с, запускает Kvist на каждую задачу
  и пересылает NDJSON-события Kvist без изменений в конверте `{"type":"event","task_id",...}`.
* **Kvist** — неизменённое ядро, запущенное как `--frontend stdio-multi` (UI_API.md, режим B).
  Своего протокола поверх каталога событий облако не добавляет.
* **Фронтенд** (`frontend/`) — статические файлы без фреймворка. Страница тарифов отдаётся
  готовым HTML, ею можно пользоваться до запуска скриптов.

## Потоки данных

### От регистрации до первой задачи (воронка)

1. `pricing_view` — страница тарифов, пробный выбран заранее. Кнопка — обычная ссылка на
   `/auth/github/login`.
2. `github_login` — GitHub OAuth (только scope `read:user`). Callback создаёт или обновляет
   пользователя, ставит cookie сессии и **запускает создание машины в фоне**, а уже потом
   делает редирект.
3. `checkout_open` → `card_added` — пробный период стартует сразу; платный тариф отправляет
   на страницу оплаты Platega (или dev-заглушка, пока `BILLING_ENABLED=false`). Тариф появляется,
   когда сервер сам спросил Platega и увидел подтверждённый платёж.
4. `key_valid` → `first_task_started` → `first_task_done` — онбординг на одном экране: плитка
   провайдера, ключ (проверяется одним дешёвым запросом через сервер сразу после вставки),
   репозиторий, одна из трёх готовых задач, «Запустить». Машина всё это время просыпается.

### Задача

```
браузер POST /api/tasks ─▶ limits.admit() ─▶ queued | starting
                                   │
                   машина спит? provider.wake() ─▶ раннер подключается ─▶ gateway шлёт start_task
                                                                          {goal, repo, key, limits}
раннер: git clone → запуск kvist (ключ только в его окружении) → {"type":"goal"} в stdin
NDJSON из stdout kvist ─▶ раннер вычищает ключ ─▶ gateway ─▶ task_events (значимые события)
                                                          └▶ живая рассылка в сокеты браузеров
статус задачи выводится из событий: task_state running/awaiting_input/paused, final, error
turn_end ─▶ раннер закрывает stdin (или держит его на фоновое окно тарифа) ─▶ ключа больше нет
```

Ответ на `input_request` идёт браузер → сервер → раннер → stdin Kvist без изменений. Пауза и
отмена — собственные сообщения Kvist `{"type":"pause"}` / `{"type":"cancel"}`.

### Разговор (новые сообщения в той же задаче)

Задача — это сессия: после первого ответа человек продолжает ей писать.

```
браузер POST /api/tasks/{id}/messages {text}
   статус running / waiting_for_user ─▶ {"type":"message"} runner'у ─▶ Kvist ставит в очередь за ходом
   статус done / paused / cancelled / failed ─▶ pending_text = text, admit() ─▶ start_task {goal: text, session, follow_up}
                                                                   │
        runner: тот же процесс, если он ещё жив (дописывает ход или его держит фоновая работа);
                иначе новый Kvist: `command session switch <session>` ─▶ затем цель
```

* Текст сохраняется и как событие `user` в `task_events`, поэтому перезагруженная страница показывает весь
  разговор (собственный журнал ядра до сервера не доходит). У задач из прошлого первого `user` нет; страница
  ставит цель перед историей.
* `session` — имя, которое Kvist дал разговору (последнее событие `session`, иначе первое `hello`).
  `Task.pending_text` хранит сообщение, пока Kvist на машине не скажет, что оно у него есть (`hello` или
  `task_state: running`): спящая машина или тариф без свободного места ничего не теряют.
* Runner держит Kvist живым после `turn_end` только пока за этим ходом стоит сообщение (`_goals_waiting`);
  в остальном он по-прежнему закрывает stdin в конце хода, так что ключа модели нет ни в одном процессе, пока агент
  простаивает.
* Запоздавший `task_exit` прошлого запуска не заканчивает новый (`pending_text` при `starting`/`queued`), а
  сообщение, дошедшее до только что закончившегося запуска, возвращается как `message_undelivered` и запускает
  следующий.
* Каждому сообщению нужны часы, ключ и подписка, как первой цели (`can_run`); пришедшее при статусе
  `queued`/`starting` отклоняется с `not_ready` (409).

### Heartbeat

Каждые 15 с, а также сразу при изменении набора, раннер шлёт
`{"type":"heartbeat","running":[id задач]}`. Сервер списывает интервал между двумя соседними
heartbeat (см. ниже). Никакой другой сигнал списания не создаёт.

### Экспорт архива

`POST /api/machines/{id}/export` (вся машина) или `POST /api/tasks/{id}/export` (папка одной
задачи) создаёт строку `exports`, будит машину при необходимости и просит раннер через сокет.
Раннер упаковывает папку в `.tar.gz` и загружает её HTTP-запросом `PUT` с токеном машины.
Браузер опрашивает экспорт и скачивает его. Экспорт идёт через раннер, а не через провайдера,
поэтому одинаково работает на любом хостинге.

### Вход через ChatGPT (`chatgpt.py`)

Подписка ChatGPT клиента может оплачивать его модель вместо API-ключа. Вход идёт через сервер, поэтому на компьютере
клиента ничего не слушает порт:

1. `POST /api/chatgpt/start` открывает попытку (3 минуты, одноразовая, привязана к вошедшему клиенту) и возвращает
   адрес OpenAI. В базе только хэш её `state`; PKCE-verifier зашифрован.
2. OpenAI возвращает браузер на `/auth/chatgpt/callback`. Попытка находится по этому state, сразу удаляется, а её
   код меняется на токены.
3. Токены лежат одним зашифрованным блоком в строке пользователя (их нужно отправлять обратно в OpenAI, поэтому
   хэш бесполезен). Токен личности читается без проверки подписи: он пришёл прямо от точки выдачи токенов OpenAI по
   TLS (OpenID Connect Core 3.1.3.7).
4. Refresh-токен заменяется при каждом использовании, поэтому продлевает его только `fresh_access_token`: под
   блокировкой на клиента и вне транзакции базы. Машина получает только короткоживущий access-токен.
5. Раз в сутки (`CHATGPT_CHECK_SECONDS`) каждый сохранённый вход продлевается. Если OpenAI отказывает, вход получает
   состояние `needs_login`, и клиент входит заново; недоступность OpenAI ничего не меняет.
6. Задача клиента с ChatGPT стартует без ключа: `start_task` несёт access-токен (`chatgpt`), провайдер Kvist —
   `chatgpt`. Раннер записывает токен в конфиг Kvist (`home/.kvist/config.json`) как «одолженный» аккаунт, в той
   форме, которую держит ядро, обслуживающее чужой фронтенд, и скрывает его в событиях, как ключ. Каждые четыре
   минуты сервер смотрит на подключённые машины таких клиентов и шлёт `chatgpt_access`, если токен сменился (он
   продлевается за десять минут до конца); Kvist перечитывает конфиг при каждом запросе, поэтому долгая задача
   не обрывается. Потерянный вход ставит задачу на паузу (`invalid_key`), а не роняет её.

### Адреса сессий и кто их открывает

У каждой задачи есть **публичный id** (`tasks.public_id`: 72 случайных бита, url-safe; не номер строки и не
переиспользуется), и рабочее место показывает каждую сессию по её адресу, **`/pixel/s/<id>`** (черновик в проекте
— `/pixel/p/<проект>`). Набрать адрес, пойти по ссылке или обновить страницу — значит открыть эту сессию без
единой кнопки; адресная строка следует за тем, что перед глазами, так что «назад» и «вперёд» переключают сессии.

Страница по такому адресу для всех одна (`pixel/index.html`); то, что она показывает, она спрашивает у API. API
находит сессию только для владельца: `GET /api/sessions/<id>` (и `/api/tasks/{n}`, `/events`, `/stream`, маршруты
экрана) отвечают другому аккаунту так же, как на несуществующий id (404), а невошедшего отправляют входить и
возвращают на тот же адрес. Страница пишет «такой сессии нет, или она принадлежит другому аккаунту», не уточняя,
что именно. Знание id сессии никому, кроме владельца, ничего не открывает.

Рабочее место ещё и предупреждает заранее: нет пробного периода, нет часов или их мало (меньше 30 минут или 10%
тарифа), нет ключа модели, ещё нет проекта, сервер в ошибке, задача остановилась (и почему) или упала
(`cloud.warnings`, `views/notices.js`).

### Проекты

Проект — именованная папка на машине человека: **пустая** (только имя) или **клон одного из его публичных
репозиториев на GitHub** (`GET /api/github/repos`). Задачи (сессии) принадлежат проекту и работают в его папке, так
что то, что оставила одна, находит следующая; прежние задачи (без `project_id`) сохраняют свою папку (`task-N`).

* **Имена не повторяются.** Имя — это папка (пробелы становятся дефисами), и сравнивается оно без учёта
  регистра: «My app», «my app» и «my-app» — один проект: `409 name_taken`; это держит база
  (`UNIQUE(user_id, folder_key)`), а сообщение даёт предварительная проверка. Можно: буквы, цифры, пробелы,
  точки, дефисы, подчёркивания, не больше 60 знаков; нельзя `/`, точку или дефис в начале и `task-<цифры>` (так
  называются папки прежних задач). Двое людей могут назвать проект одинаково: их машины разные.
* **Папка создаётся на машине** (`prepare_project`: создать или склонировать) сразу при добавлении проекта, если
  машина не спит, и для всех проектов при каждом подключении runner'а, так что проект, добавленный пока машина
  спала, появится, когда она проснётся. Существующая папка не трогается. Runner отказывает в имени папки, которое
  не простое имя (`project_dir`), кто бы его ни прислал.
* **Одна сессия на задачу в общей папке.** Kvist хранит сессии по папке, и без этого задача продолжила бы последний
  разговор проекта. Сессия задачи называется `task-<id>`: первый запуск открывает её (`command new`), следующие
  возвращаются в неё (`command session switch`); первый запуск, нашедший имя занятым (умер, открыв её), тоже
  переключается.
* Экспорт задачи упаковывает папку её проекта (`folder` в сообщении `export`).

### Экран агента (приватный)

Скиллы браузера и рабочего стола рисуют на виртуальном экране, который Kvist отдаёт на loopback-адресе
машины под секретным токеном. То, что агент там делает, так же приватно, как его файлы:

1. **Адрес и токен не покидают машину.** Runner переписывает каждое событие `screen` (`url`,
   `stream_url`, `frame_url` обнуляются) и оставляет адрес у себя. Сервер ещё раз пропускает событие
   через белый список (`screens.public_view`) и подставляет в `frame_url` свой адрес.
2. **Кадры тянутся, только пока владелец смотрит.** Страница владельца опрашивает
   `GET /api/tasks/{id}/screens/{screen}/frame.jpg`; каждый запрос продлевает аренду на машине на
   10 с (`screen_watch`), и runner берёт JPEG шириной 960 px у своего loopback-вьюера примерно дважды
   в секунду, пока аренда не истечёт. Кадры идут по единственному аутентифицированному сокету машины
   как `screen_frame`; если связь упала или забита, кадр выбрасывается, а не копится в очереди.
3. **Только память.** Кадры лежат в одном словаре процесса (`ScreenStore`, не больше 64, каждый не
   больше 1 МБ и с проверкой JPEG-заголовка), протухают через 10 с и забываются, когда экран закрыт
   или задача завершена. Их нет в базе, в `task_events`, в логах и в экспортах; само событие
   `screen` тоже не сохраняется.
4. **Только владелец.** Маршрут находит задачу тем же `owned_task`, что и остальные: чужой аккаунт,
   администратор и неавторизованный получают ответ как для несуществующей задачи (404; 401 без входа),
   без намёка, что экран вообще есть. Живой поток так же отказывает не-владельцам. Нужен заголовок
   `X-Kvist-Client`, которого не может поставить `<img>` на чужом сайте; ответ `private, no-store`.
5. **Машина говорит только за свои задачи.** `screen_frame` для чужой задачи отбрасывается и
   логируется.

Тесты: `backend/tests/test_screens.py` (изоляция аккаунтов, админ, без входа, поток, хранение, лимиты)
и `runner/tests/test_screens.py` (адрес вырезан, загрузка только с loopback, аренда).

## Правила учёта часов

`ledger_entries` — журнал только на добавление. У каждой строки знаковое значение `seconds` и
вид `kind`: `grant` (+, часы тарифа на период), `purchase` (+, купленный пакет), `refund`
(+, исправление с причиной `reason`), `usage` (−, время агента). Баланс периода — сумма его строк.

1. **Что списывается.** Время, пока у задачи статус `running`: агент думает, ждёт модель или
   выполняет команду. `waiting_for_user`, `paused`, `done`, `cancelled`, `failed` и `queued`
   бесплатны.
2. **Считаются только heartbeat.** На heartbeat *k* (часы сервера, никогда не раннера) сервер
   списывает `floor(t_k) − floor(t_{k−1})` секунд, если heartbeat *k−1* назвал хотя бы одну
   задачу, разрыв не больше `HEARTBEAT_MAX_GAP_SECONDS` (по умолчанию 45 с, три пропущенных
   удара) и эти задачи `running` и на сервере. За разрыв длиннее не списывается ничего: учёт
   остановился на последнем heartbeat и продолжится со следующего.
3. **Параллельные задачи считаются один раз.** Один интервал одной машины — одно списание,
   сколько бы задач в нём ни было: объединение по машине, а не сумма по задачам. Секунды
   делятся между задачами только для показа (`s // n` каждой, остаток по секунде в порядке id),
   так что лента по задачам в сумме даёт ровно списанное.
4. **Посекундно, показ в минутах.** Строки хранят целые секунды; полы абсолютных отметок
   времени складываются телескопически, поэтому между heartbeat ни одна доля не теряется и не
   добавляется. Интерфейс показывает `floor(seconds / 60)` минут.
5. **Никаких UPDATE и DELETE.** ORM отказывает в обоих для `LedgerEntry` (защита на уровне
   mapper и массовых запросов), а миграция ставит триггеры в базе, которые их прерывают.
   Исправление — новая строка `refund` с причиной.
6. **Часы кончились посреди задачи.** Сервер перестаёт списывать на нуле (в минус не уходит) и
   шлёт раннеру `pause` с отсрочкой 5 минут: Kvist встаёт на паузу в ближайшей безопасной точке,
   обычно после текущей команды; если через 5 минут пауза не наступила, раннер шлёт `cancel`,
   который сохраняет чекпоинт. Задача получает статус `paused` с причиной `hours_exhausted`.
   Ничего не удаляется, после покупки часов задачу можно продолжить.
7. **Сбой провайдера модели.** Неверный ключ (401/403) ставит задачу на паузу сразу. 429 и 5xx
   считаются, только если длятся 5 минут без единого успешного вызова модели; тогда задача
   встаёт на паузу с причиной `provider_unavailable`. Пауза — значит часы стоят. Ожидание
   модели в эти 5 минут — обычное время `running`.

## Лимиты (`limits.py`)

* **Параллельные задачи.** Задача сверх лимита тарифа получает `queued` и стартует, когда
  освобождается место. Место занимают `starting`, `running` и `waiting_for_user`; `paused` нет.
* **Время команды.** Передаётся раннеру с каждой задачей. Ядро сейчас ограничивает обычную
  команду 300 с, это меньше лимита любого тарифа, так что на деле лимит касается фоновых задач:
  задача старше лимита заставляет раннер остановить всю задачу агента (`cancel`, чекпоинт
  сохраняется, причина `command_time_limit`).
* **Фон.** При `background_minutes = 0` (пробный) Kvist запускается без `--wake`, и фоновые
  задачи умирают вместе с ходом. Иначе раннер держит Kvist после `turn_end`, пока идут фоновые
  задачи, но не дольше окна тарифа, затем закрывает. Фоновое время не списывается, ход после
  пробуждения списывается.
* **Размер машины.** На local-провайдере раннер оборачивает Kvist в
  `systemd-run --user --scope -p MemoryMax=… -p CPUQuota=…`, если systemd доступен, и каждая
  запущенная агентом команда наследует лимиты. Без systemd раннер пишет предупреждение в лог и
  работает без лимитов.

## Секреты

* Ключи моделей шифруются Fernet (`KVIST_CLOUD_MASTER_KEY`, только из окружения). API отдаёт
  только последние четыре символа.
* Ключ расшифровывается только для сообщения `start_task`. Раннер кладёт его в окружение Kvist
  и больше никуда, вычищает его из каждой строки вывода Kvist перед пересылкой и забывает, когда
  процесс завершается. Сервер вычищает пересланные события второй раз.
* В логи не попадают тела запросов. Необработанная ошибка возвращает простой текст и код для
  поддержки; трейсбек уходит в лог с вычищенными секретами.
* Local-провайдер запускает раннер с чистым окружением, так что мастер-ключ и секрет сессий
  сервера на машину не попадают.
* `tests/test_secret_leaks.py` ищет ключ в логах, ответах API, событиях и исключениях.

## Правила честности в интерфейсе

Длительность пробного периода и цена после него видны на странице тарифов рядом с кнопкой, до
ввода карты. Отмена — одна кнопка в настройках и одно подтверждение. За два дня до конца
пробного периода на дашборде баннер и в очередь ставится письмо: «Через 2 дня спишем $15».
Никаких таймеров, ложной срочности и предвыбранных платных опций.

## Производительность

Страница тарифов заранее отрисована для каждой локали, CSS встроен; кнопка — ссылка, так что
страница интерактивна, как только разобран HTML. Бандл приложения — один ES-модуль с обеими
локалями. Бюджеты проверяет `frontend/build.mjs`: первый экран ≤ 100 KB по сети.

Результаты Lighthouse записаны в разделе «Lighthouse» ниже.

## Lighthouse

Замер 2026-11-05, Lighthouse 12.8.2 (`frontend/tools/lighthouse.sh`), против `scripts/dev.sh` на
этом компьютере: мобильный форм-фактор, медленный 3G (задержка 400 мс, 400 кбит/с, CPU медленнее
в 4 раза). Первый экран, который видит человек, — страница тарифов; два других — экраны воронки
после входа.

Chrome по-настоящему режет сеть (`METHOD=devtools`, по умолчанию):

| Тарифы, en | 100 | 100 | 100 | 0.56 с | 0.60 с | **0.57 с** | 0 | 59 KB |
| Тарифы, ru | 100 | 100 | 100 | 0.64 с | 0.64 с | **0.64 с** | 0 | 72 KB |

Собственная модель Lighthouse (`METHOD=simulate`) на тех же страницах: тарифы en 3.2 с, ru 4.0 с,
онбординг 5.3 с TTI. Модель считает веб-шрифт блокирующим первую отрисовку, что бы ни говорил
`font-display`; с `optional` браузер сразу рисует системным моноширинным, это и показывает замер
devtools. Скрипт сохраняет оба отчёта в `.lighthouse/`.

Первый экран укладывается в задание: меньше 100 KB, интерактивен за 0.6 с. Экраны после входа —
2.2–2.4 с: HTML, один бандл на 22 KB и один круг к API по 400 мс каждый. Что опустит их ниже
1.5 с (в MVP не сделано): встроить бандл в оболочку (минус круг; нужен хеш в CSP) и собирать
бандл на каждую локаль (−6 KB).

Что сдвинуло числа: gzip на всех ответах (HTML тарифов с 20 KB до 5.5 KB), `font-display: optional`
вместо `swap` лендинга (нет поздней перекладки текста, шрифт не входит в первую отрисовку), отказ
от preload шрифта и данные первого экрана, которые сервер кладёт прямо в страницу.

## Решения

Где задание оставляло выбор, взят простой вариант, и он записан здесь.

1. **Ветка.** В задании сказано «работай в main», а CLAUDE.md репозитория запрещает коммитить
   прямо в `main`. Работа коммитится в `experimental` и попадает в `main` fast-forward'ом после
   проверки.
2. **Источник стиля.** В задании назван `web/`, а лендинг лежит в `site/`. Его токены и шрифты
   скопированы во `frontend/` (вне `cloud/` ничего не меняется).
3. **Без фреймворка на фронтенде.** Тот же стек, что у лендинга (ванильный JS, esbuild). Один
   рантайм фреймворка съел бы большую часть бюджета первого экрана.
4. **Провайдер «другой» — любой OpenAI-совместимый адрес** (base URL, ключ, модель). Kvist
   работает с ним через свой провайдер `omniroute`, настроенный из окружения. Локальный dev-шлюз
   модели подключается так же, поэтому отдельного dev-провайдера нет.
5. **Один ключ на аккаунт.** Хранится в строке пользователя (`model_provider`,
   `model_key_enc`, `model_key_last4`); таблицы ключей нет.
6. **Своя папка на каждую задачу** (`work/task-<id>` на машине). Параллельные задачи никогда
   не правят один и тот же checkout; архив задачи — эта папка, архив машины — все они.
7. **Только публичные репозитории.** Вход просит `read:user` и ничего больше: просьба о `repo`
   на первом экране отпугивает. Приватным репозиториям позже понадобится отдельное разрешение.
8. **Часы не переносятся.** Часы тарифа и купленные пакеты принадлежат текущему расчётному
   периоду. Пробный период — отдельный период в 7 дней.
9. **5 минут отсрочки после конца часов бесплатны.** Учёт останавливается на нуле, баланс в
   минус не уходит.
10. **Подтверждения.** Kvist работает с `--approval-mode ask` и `AGENT_WRITE_APPROVAL=0`:
    опасная команда по-прежнему спрашивает человека (статус `waiting_for_user`, часы стоят),
    запись файлов в папке задачи — нет. Сеть в песочнице разрешена (`AGENT_SANDBOX_NET=allow`):
    облачная машина без сети не поставит зависимости.
11. **Ошибки провайдера распознаются по тексту ошибок Kvist** (шаблоны 401/403, 429, 5xx).
    Структурное событие было бы лучше, см. «Нужные правки ядра».
12. **Dev-вход.** При `AUTH_DEV_LOGIN=true` и ненастроенном GitHub-приложении кнопка GitHub
    входит локальным dev-пользователем. Сервер отказывается так стартовать, если `PUBLIC_URL`
    не loopback-адрес.
13. **Один процесс сервера.** Живая рассылка событий — pub/sub внутри процесса. Нескольким
    экземплярам сервера понадобится PostgreSQL `LISTEN/NOTIFY` или аналог; для MVP не нужно.
14. **Задача на паузе отпускает машину.** На паузе процесс Kvist завершается (а с ним и ключ);
    продолжение запускает новый процесс с командой Kvist `resume` и ключом, присланным заново.
15. **Письма ставятся в очередь, а не отправляются.** Напоминание о конце пробного периода
    пишется в таблицу `outbox`; подключение почтового провайдера вне MVP.
16. **`font-display: optional`**, а не `swap`, как на лендинге. На медленном 3G поздняя подмена
    шрифта сдвигала самую большую отрисовку на секунды и перекладывала текст; теперь первый визит
    может быть нарисован системным моноширинным, а следующий — Kvist Mono из кеша.
17. **Оболочка приложения несёт данные первого экрана**
    (`<script id="boot" type="application/json">`): пользователь, подписка, настройки биллинга,
    сводка ключа, провайдеры. Это экономит один-два круга к серверу; следующие экраны внутри
    приложения спрашивают API как обычно.
18. **Ответ в чате завершает задачу как выполненную.** Kvist заканчивает чат-ход событиями
    `message` + `turn_end` без `final` (UI_API.md); ход без ответа и без `final` — сбой.
19. **Локальная модель — фейковый OpenAI-совместимый сервер** (`scripts/fake_model.py`), который
    ведёт настоящее ядро по короткому сценарию; подключается как провайдер «Другой». Он отвечает на
    пробу инструментов ядра (`ping`) и на роутер ролей, так что ядро работает как с настоящей
    моделью.
20. **Lighthouse записан с реальным троттлингом** (`devtools`) рядом с моделью Lighthouse
    (`simulate`), потому что модель не учитывает `font-display` (см. «Lighthouse»).
21. **Окружение Kvist задаёт раннер.** Kvist работает с `AGENT_WRITE_APPROVAL=0` и
    `AGENT_SANDBOX_NET=allow` (решение 10) и со своими `HOME` и `KVIST_CONFIG_DIR` внутри папки
    машины, так что локальная машина никогда не берёт личный конфиг Kvist разработчика.

## Нужные правки ядра

Не сделаны (задание запрещает менять что-либо вне `cloud/`); перечислены здесь и в итоговом
отчёте.

1. Структурное событие `provider_error` (`status_code`, `retrying`, `retry_in`) вместо
   сопоставления текста в сообщениях `error`/`status`.
2. Входящее сообщение `{"type":"job_stop","job_id"}`, чтобы раннер мог остановить одну фоновую
   задачу, вышедшую за лимит времени, а не всю задачу агента.
3. Настраиваемый потолок времени обычной команды (`MAX_SHELL_TIMEOUT_SECONDS` зашит на 300 с),
   чтобы лимиты тарифов 30 мин / 2 ч / 6 ч на команду значили то, что написано.
