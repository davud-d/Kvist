# Развёртывание Kvist Cloud

*(English version: [DEPLOY.md](DEPLOY.md))*

Один сервер Debian 12: впереди nginx, за ним управляющий сервер (один процесс), PostgreSQL 15. Бэкапы идут на
вторую машину, см. [BACKUP.ru.md](BACKUP.ru.md).

Машины клиентов — виртуальные машины KVM на этом же сервере (см. «Машины клиентов» ниже), так что один сервер — это
весь продукт: вход, оплата (или выдача доступа вручную, пока оплата выключена), машины, бэкапы.

## Раскладка на сервере

```
/opt/kvist-cloud/releases/<id>/   по папке на каждую выкладку (код, свой .venv, vendor/)
/opt/kvist-cloud/current          ссылка на живой релиз; переключение — одна атомарная смена ссылки
/etc/kvist-cloud/cloud.env        все настройки и секреты (0640 root:kvist-cloud)
/var/lib/kvist-cloud              каталог данных (экспорты), пишет только сервис
```

В `vendor/` лежат пять крошечных файлов ядра, которые импортирует сервер (`deploy/kernel-files.txt`); весь
репозиторий на сервере не нужен.

## Первый раз

```bash
# PostgreSQL и база
sudo apt install postgresql nginx python3-venv rsync curl
sudo -u postgres createuser kvist_cloud --pwprompt
sudo -u postgres createdb -O kvist_cloud kvist_cloud

# пользователь сервиса и каталоги
sudo adduser --system --group --home /var/lib/kvist-cloud kvist-cloud
sudo install -d -o kvist-cloud -g kvist-cloud /var/lib/kvist-cloud
sudo install -d /opt/kvist-cloud/releases /etc/kvist-cloud

# настройки: свежие секреты, дальше заполни остальное (скрипт подскажет что)
sudo scripts/gen-secrets.sh /etc/kvist-cloud/cloud.env
sudoedit /etc/kvist-cloud/cloud.env
```

`KVIST_CLOUD_MASTER_KEY` из этого файла сохрани в менеджере паролей и на бумаге, **не** в бэкапах сервера.
Заполни `PUBLIC_URL`, `DATABASE_URL` (`postgresql+psycopg://…`), `KVIST_CLOUD_DATA_DIR`,
`GITHUB_CLIENT_ID/SECRET` (callback `<PUBLIC_URL>/auth/github/callback`), `ADMIN_GITHUB_LOGINS`, значения Platega
или `BILLING_ENABLED=false`.
`CHATGPT_SIGNIN` оставь выключенным (по умолчанию так и есть): «Вход через ChatGPT» отправлял бы подписки многих
клиентов с одного адреса этого сервера, а именно такое ищет защита OpenAI от злоупотреблений, и банят при этом
аккаунты клиентов. Включай только после согласия OpenAI; пока выключен, провайдер не предлагается, а его маршруты
отвечают 503.

Debian 13 тоже подходит (PostgreSQL 17 вместо 15; см. замечание о версиях в [BACKUP.ru.md](BACKUP.ru.md)). Если
впереди Cloudflare, а в nginx на хосте уже есть Origin-сертификат, возьми `deploy/nginx/kvist-cloud-cloudflare.conf`
вместо `kvist-cloud.conf` (certbot не нужен; про лимит 100 МБ на загрузку через прокси читай в его заголовке).

Сервис и nginx (подставь вместо `cloud.example.org` своё имя и выпусти сертификат):

```bash
sudo cp deploy/systemd/kvist-cloud.service /etc/systemd/system/ && sudo systemctl daemon-reload
sudo sed 's/cloud.example.org/<твоё-имя>/g' deploy/nginx/kvist-cloud.conf | sudo tee /etc/nginx/conf.d/kvist-cloud.conf
sudo certbot --nginx -d <твоё-имя>      # или свой сертификат
sudo systemctl enable kvist-cloud
```

Бэкапы настрой до первой выкладки ([BACKUP.ru.md](BACKUP.ru.md)): выкладка откажется мигрировать без свежего дампа.

## Каждая выкладка

На твоём компьютере:

```bash
scripts/deploy.sh user@server
```

Скрипт собирает фронтенд, копирует дерево в новый релиз (ни в какой git-remote ничего не отправляется) и запускает
на сервере `activate_release.sh`, который по порядку:

1. ставит релиз в его собственный venv и **проверяет конфигурацию** (`python -m kvist_cloud.prodcheck`): https,
   PostgreSQL, настоящий провайдер, вход настроен, есть админ, нет dev-флагов, мастер-ключ валиден;
2. делает бэкап базы (без настроек бэкапа отказывается; `KVIST_SKIP_BACKUP=1` отменяет осознанно);
3. мигрирует базу;
4. переключает ссылку `current`, перезапускает сервис и ждёт `/healthz` до 60 с;
5. **если сервис не поднялся, возвращает прежний релиз** и завершается с ошибкой;
6. запускает `python -m kvist_cloud.integrity` (схема на head, защита ledger от правок, знаки и ссылки в ledger,
   оплаченные заказы, которые ничего не выдали, дубли машин) и оставляет 5 последних релизов.

Пока при откате старый релиз работает уже на мигрированной базе, **миграция должна оставаться совместимой с
предыдущим релизом**: сначала добавляем колонки, удаляем их только в следующем релизе.

После этого, откуда угодно: `scripts/smoke_prod.sh https://<твоё-имя>`. Он смотрит снаружи: HTTPS и
сертификат, `/healthz`, заголовки безопасности, отсутствие `/docs`, отказ анонимам на `/api/me` и `/admin`, что вход
ведёт на GitHub (а не на dev-вход), и что WebSocket раннеров проходит через прокси.

## Машины клиентов (`MACHINE_PROVIDER=libvirt`)

Машина каждого клиента — виртуальная машина KVM на самом сервере (гость Debian 12, по одной на аккаунт). Серверу
нужен `/dev/kvm`: железный сервер или VPS с вложенной виртуализацией. Впиши `MACHINE_PROVIDER=libvirt` в `cloud.env`.

- **На твоём компьютере** нужен podman или docker: `deploy.sh` собирает колёса для гостя (kvist, kvist-runner и все
  зависимости) в контейнере Debian 12, потому что Python гостя 3.11, какой бы ни был у хоста. Пока исходники не
  менялись, результат берётся из кэша; колёса лежат в `/opt/kvist-cloud/wheels` и принадлежат root.
- **При каждой выкладке** `activate_release.sh` запускает `scripts/install_vm_host.sh`: ставит KVM/libvirt/nftables,
  кладёт два скрипта, работающих от root, в `/usr/local/lib/kvist-vm/`, загружает правила сети и запускает сокет
  помощника.
- **Сервер остаётся без привилегий.** Он просит маленького помощника от root (`vm_ctl.py`) через
  `/run/kvist-vm.sock`, который открывается только пользователю сервера; помощник проверяет каждое поле и может
  трогать только домены `kvist-<число>`. VM создаёт `setup_vm.sh`; раннер внутри сам подключается к шлюзу со своим
  токеном, внутрь никто не заходит (ни ssh, ни открытых портов).
- **Изоляция** (`deploy/vm-firewall.nft`): VM не достаёт до другой VM, до служб самого хоста, частных сетей и
  адреса метаданных провайдера, только до интернета. В сети (`deploy/vm-network.xml`) выключен DNS libvirt: хост,
  у которого уже есть DNS-сервер, не делит с ним порт 53, а гости получают публичные резолверы по DHCP.
- **Первая загрузка занимает минуты**: гость ставит пакеты (браузер, виртуальный экран, сборочные инструменты).
  Сервер ждёт новую машину до 20 минут, а пробуждение позже — 3.
- **Потолки** — самый большой тариф (4 vCPU, 8 ГБ, 150 ГБ); `setup_vm.sh` проверяет их ещё раз и отказывается, если
  на хосте останется меньше 2 ГБ памяти или 20 ГБ диска.

## Ротация мастер-ключа

```bash
sudo /opt/kvist-cloud/current/scripts/rotate_master_key.sh start    # бэкап, новый ключ вперёд, перешифровка, рестарт
# проверь сайт, сохрани НОВЫЙ ключ вне сервера
sudo /opt/kvist-cloud/current/scripts/rotate_master_key.sh finish   # убрать старый ключ
```

**Старый ключ храни офлайн, пока существуют бэкапы старше ротации** (по умолчанию 6 месяцев): секреты в них
зашифрованы им.

## Что нужно знать

- **Только один воркер.** Шлюз раннеров, шина событий и кадры экранов живут в памяти процесса; юнит запускает
  `--workers 1`. Несколько процессов разведут раннеры и браузеры по разным процессам.
- **Перезапуск обрывает открытые сокеты**: раннеры и браузеры переподключаются сами, но выкладка во время задачи
  заметна. Выкладывай, когда тихо.
- **`pip install` ходит в PyPI** на сервере во время выкладки, и версии зависимостей пока нигде не зафиксированы.
- **Проверено** в контейнере Debian 12 на PostgreSQL 15 с заглушкой вместо `systemctl` (первая выкладка, бэкап
  перед миграцией, smoke, ротация ключа, откат релиза, который не стартует, чистка релизов) и конфиг nginx через
  `nginx -t` плюс настоящее WebSocket-рукопожатие; затем на настоящем сервере Debian 13 с настоящим systemd:
  `deploy.sh` по ssh и rsync, таймеры бэкапа и тест восстановления на втором хосте, провайдер VM с двумя живыми
  гостями (первая загрузка и подключение раннера, сон, пробуждение, удаление; правила изоляции, проверенные
  изнутри гостей). **Не проверено:** certbot, запуск задачи на машине клиента с настоящим ключом модели, много VM
  одновременно.
